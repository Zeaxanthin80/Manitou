01

What Docker solves

"Works on my machine" used to be a real plague. You install PostgreSQL 14, a teammate has 16, production runs 15 — each with slightly different config. Bugs appear only in certain environments, and setup is pages of "install X, then Y, then hope."

Docker's idea: package an application together with its entire runtime environment — OS libraries, dependencies, exact versions — into one portable unit that runs identically on your laptop, a teammate's Windows machine, or an AWS server.

Image vs. container

The distinction that trips everyone up. An image is a frozen, read-only blueprint — like a recipe, or a class in code. A container is a running instance of that image — the actual dish, or an object instantiated from the class.

You've already lived this

postgres:16-alpine in your compose file is the image — a pre-built package Docker downloads from Docker Hub. Running docker compose up started a container from it, which is why docker ps shows a running process.

You could start five containers from that one image. Each would be an independent, isolated Postgres server. You never "installed Postgres" in the traditional sense — you ran a known-good pre-built package.

Three words worth knowing

Dockerfile Instructions for building a custom image. You'll write one in Phase 6 to package FastAPI. You haven't needed one yet because Postgres ships a pre-built image.
Volume Persistent storage that survives the container being deleted. Exactly what manitou_pgdata does — without it, removing the container would wipe every row you seeded.
Registry Where images are stored and distributed. Docker Hub is the public one; AWS ECR is the one you'll push your own image to.
02

The Docker components

Read top to bottom as "furthest from the metal" to "closest to it." Everything above the Engine is ultimately a way of talking to the Engine.

L1
Docker DesktopUsed

A full application bundling Engine, CLI, Compose, and Buildx, plus a GUI — and on Mac and Windows, a lightweight Linux VM, since those systems have no Linux kernel to run containers natively.

The "everything included" package. On Linux you don't strictly need it — Engine and CLI install directly — but it's a common convenience layer, which is how you have it on Ubuntu.

L2
Docker Composedocker composeUsed

A CLI plugin that reads your YAML file and tells the Engine to start and stop multiple containers together, on one machine.

Sits on top of the CLI and Engine — a coordinator, not a separate runtime. Note the space: docker compose is the current V2 plugin. The hyphenated docker-compose is the retired V1 standalone binary, which is why it wasn't found on your machine.

L2
Docker Builddocker build · Buildx · BuildKitPhase 6

The subsystem that turns a Dockerfile into an image. docker build is the command, BuildKit is the modern engine behind it, Buildx is the plugin adding features like multi-platform builds.

You meet this when you package your FastAPI app. Untouched so far because Postgres's image was already built for you.

L3
Docker CLIdockerUsed

The command-line client that sends instructions to the Engine over an API.

What you type. It does nothing on its own without an Engine to talk to.

L4
Docker EnginedockerdUsed

The background daemon that actually builds, runs, and manages containers.

The bottom of the stack. Everything else is a way of talking to this.

EXT
Docker HubUsed

The public registry storing images — where postgres:16-alpine actually lives and gets downloaded from.

A storage and distribution service, unrelated to running anything. Off to the side of the stack, not part of it.

—
KubernetesNot needed

Not a Docker product at all. A separate project, originally Google's, for orchestrating containers across many machines — auto-scaling, self-healing, cluster load balancing.

Compose orchestrates containers on one machine for local dev; Kubernetes orchestrates across a fleet. They get conflated because Docker Desktop bundles an optional single-node Kubernetes. You won't need it — AWS ECS Express Mode does that job for you, one level removed (App Runner filled this role until it closed to new customers in April 2026).

Chain of command

What happens between typing a command and a container existing.

You type a command │ ├─▶ Docker CLI (or Compose, calling the CLI's API) │ ├─▶ Docker Engine (the daemon doing the actual work) │ ├─▶ creates / runs a container, from an image │ └─▶ image was either pulled from Docker Hub or built by you via Docker Build
04

What PostgreSQL is

Docker is just the delivery mechanism. The actual thing running inside that container is PostgreSQL — a relational database management system.

"Relational" means data lives in tables of rows and columns, and tables reference each other through keys — exactly what Section 6 of your plan describes. A product_variants row points at a products row via product_id. The relationships between tables are as much part of the design as the tables themselves.

Why Postgres, out of the many options

ACID transactions A set of changes either all happen or none do. Exactly why checkout wraps "create order + decrement inventory + record payment" in one transaction — if payment fails, you don't want a half-finished order sitting in the database.
Data integrity Foreign keys, unique constraints, and not-null rules are enforced by the database itself, not trusted to application code. If your API has a bug and inserts an order pointing at a nonexistent product, Postgres refuses.
JSONB The flexible, semi-structured side — what product_variants.attributes uses so different store types define their own variant dimensions without a schema change.
Extensions Optional modules that add capability to the server itself: PostGIS for geographic data, pg_stat_statements for query performance. Not relevant yet — just know the server is extensible beyond core SQL.
05

The PostgreSQL components

Simpler than Docker: there's one server, and many ways to reach it. Everything below the server is a client of some kind.

SRV
PostgreSQL serverthe "backend" · postgres processUsed

The actual database engine — stores data, enforces constraints, executes SQL.

The one thing every client below connects to. In your setup it's the process running inside the manitou_db container, listening on port 5432.

CLI
psqlUsed

The official command-line client — the one you installed via postgresql-client.

A client, nothing more. Types SQL, gets answers back. Deliberately not the full postgresql package, which would have started a second, competing server on port 5432.

GUI
GUI clientspgAdmin · TablePlus · DBeaverOptional

Visual alternatives to typing raw SQL.

Also just clients — same wire protocol as psql, different interface.

DRV
Driverpsycopg2Used

The library your application calls to connect programmatically. Not interactive, not for humans.

What SQLAlchemy uses under the hood to actually send SQL over the network. You installed it but will rarely import it directly.

ORM
SQLAlchemyPhase 1

A Python abstraction that lets you write model classes instead of raw SQL strings.

Sits on top of psycopg2 — translates your models into SQL and sends it via the driver.

MIG
AlembicPhase 1

Manages versioned schema changes — every new table, column, or index becomes a migration file committed to Git.

Sits on top of SQLAlchemy specifically. The reason your local schema and RDS schema stay identical in Phase 6.

The key insight

psql, pgAdmin, psycopg2, and SQLAlchemy can all connect to the same running server at the same time, because they all speak the same underlying wire protocol.

That's why you can have psql open in one terminal running queries by hand while your FastAPI app is connected via SQLAlchemy — one Postgres process, many clients, no conflict.

06

How they fit together

Docker isn't part of PostgreSQL, and PostgreSQL isn't part of Docker. They're independent tools that happen to compose well.

Your laptop ├── Docker container "manitou_db" │ └── PostgreSQL server, listening on port 5432 │ ▲ ▲ │ │ │ ├── psql ──────┘ │ │ (you, typing SQL by hand) │ │ │ └── FastAPI app (in your venv) ─── SQLAlchemy ── psycopg2 ──┘
Where the boundary sits

Docker's job ends at "there is a Postgres server running and reachable on port 5432." What happens inside — tables, rows, queries, constraints — is pure PostgreSQL, with zero Docker-specific behavior.

That's the whole value: the exact same Postgres, behaving the exact same way, whether it's containerized on your laptop or a managed RDS instance. Nothing about your SQL, your SQLAlchemy models, or your Alembic migrations needs to know Docker is involved.

How do I run this reliably, anywhere?

Docker's question.

How do I store and query structured data safely?

PostgreSQL's question.

Local → AWS

Which AWS service replaces which local piece, for when Phase 6 arrives.

Local, nowAWS, Phase 6Shared role
Docker Hub ECR Where images live
docker compose up ECS Express Mode Runs the container
Postgres in a container RDS Runs the PostgreSQL server
The row worth sitting with

RDS is not a different database. It's the identical PostgreSQL engine, with AWS handling patching, backups, and uptime instead of Docker handling containerization.

Nothing about your schema, models, or migrations changes when you move from one to the other. That's the point of Section 6.11 in the plan — and why developing locally against Docker is a faithful rehearsal for production, not an approximation of it.
