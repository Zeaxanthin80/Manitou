Everything below has passing tests. This walks the parts a test cannot reach: a real tracking number that opens a real parcel page, and a database refusing you, at a bare prompt, with full credentials. Tick as you go — progress survives a closed tab.

00

Before you start

Three services, and an order that has been paid for but not yet sent.

  1. Postgres, the API and the web app are all up.

    docker ps --format '{{.Names}}\t{{.Status}}'
cd backend && .venv/bin/uvicorn app.main:app --reload
cd web && npm run dev

    manitou-db-1 healthy, API on :8000, web on :3000.

  2. Pick a paid order that has not been dispatched.

    docker exec manitou-db-1 psql -U manitou -d manitou -c \
"SELECT o.id, o.total, u.email FROM orders o
   JOIN users u ON u.id=o.user_id
   LEFT JOIN shipments s ON s.order_id=o.id
  WHERE o.status='paid' AND s.id IS NULL ORDER BY o.id DESC LIMIT 5;"

    At least one row. Note the id — every step below uses it.

  3. Find a real tracking number — a genuine USPS, UPS or FedEx number from anything you have had delivered recently.

    A made-up number proves the link is built correctly and nothing more. A real one proves it reaches a parcel, which is the only claim that matters to a customer chasing a delivery.

01

Vendor · dispatch

The bare “Mark shipped” button is gone. A shipped order now needs evidence, and this is where it is collected.

  1. Sign in as admin@manitou.example and open /admin/orders/{id}.

    A Dispatch this order form with a carrier picker — and no “Mark shipped” button.

    The API refuses shipped via PATCH now, so the portal stops offering a control that would 409. It learns which ones from evidence_required, not from its own copy of the rule.

  2. Confirm the picker lists USPS, UPS and FedEx, and that “Mark cancelled” and “Mark refunded” are still ordinary buttons.

    Those two buttons are the control. A portal that hid every button would look identical on this screen and be badly wrong.

  3. Submit with the carrier blank or the number blank.

    Refused, with a sentence — not a silent no-op and not a crash.

  4. Dispatch properly: pick the carrier matching your real tracking number, paste it, submit.

    The form is replaced by a Shipment panel showing the carrier, the tracking number as a link, and one timeline entry — dispatched · admin.

  5. Reload the order list at /admin/orders.

    The order now reads shipped.

    The shipment, its first event and the status change were one transaction. An order marked shipped with no tracking number would be indistinguishable afterwards from a parcel that really went out.

02

Customer · tracking

The transparency this whole phase exists for. Before it, a customer saw a status word and no dates, no carrier and no link.

  1. Sign in as the customer who placed that order and open /orders/{id}.

    A Tracking section: Ordered, Paid and Dispatched filled; Delivered still hollow. Dates on the filled ones.

  2. Click the tracking link. This is the one step nothing automated can do for you.

    The carrier's site opens on your actual parcel — not their homepage, not a search box.

    A link that does not reach the parcel is worse than no link, because it looks like it worked. That is why the URL template must contain {tracking} and why a missing carrier yields no link at all rather than a bare homepage.

  3. View source (Ctrl-U) and search for admin@manitou.example and for recorded_at.

    Neither appears.

    The customer's shape is deliberately narrower than the vendor's. Reusing the admin's would ship a staff email address to every customer who opens an order page.

03

Vendor · delivery

Delivery is an event with a time and a source, not a status somebody types.

  1. Back on /admin/orders/{id}, press failed first.

    A new timeline entry — and the order is still shipped.

    A failed attempt means the parcel is still out with the carrier and will be retried. Only delivered moves an order.

  2. Now press delivered.

    The order reads delivered, the event buttons disappear, and the timeline holds all three entries.

  3. Reload the customer's order page.

    All four steps filled. Both timelines agree.

  4. Check what the events actually recorded.

    docker exec manitou-db-1 psql -U manitou -d manitou -c \
"SELECT status, source, occurred_at, recorded_at FROM shipment_events ORDER BY id;"

    Every source is admin.

    Which is the truth: you clicked a button, no carrier confirmed anything. That honesty is what makes the column worth having when a real carrier integration arrives — a delivery an admin asserted is not the same fact as one a carrier confirmed.

  5. Look at occurred_at beside recorded_at.

    Seconds apart, and looking redundant.

    They will be, today. They exist for the case that has not happened yet: a carrier webhook arriving Tuesday about a Monday delivery. Collapse them into one column and the customer's timeline lies, and the dispute evidence carries the wrong shipping date — on the one row where the date is the whole argument.

04

The database refuses you

The suite already asserts this. Seeing it refuse you — full credentials, bare prompt, no application in the way — is a different kind of knowing.

  1. Open a prompt and look at what is there.

    docker exec -it manitou-db-1 psql -U manitou -d manitou

SELECT id, status, source FROM shipment_events ORDER BY id;

    Your three events. Note the first id.

  2. Try to rewrite history.

    UPDATE shipment_events SET status = 'delivered' WHERE id = 1;

    ERROR: shipment_events is append-only; UPDATE is not permitted

  3. Try to erase it.

    DELETE FROM shipment_events WHERE id = 1;

    The same refusal, naming DELETE.

    Evidence an application can rewrite is not evidence. Enforced by a trigger rather than in Python, because a Python guard is one a script, a shell or an endpoint written next year can step around. This is the property a chargeback rests on.

  4. Confirm an INSERT still works — the table is append-only, not read-only. 

    INSERT INTO shipment_events (shipment_id, status, occurred_at, source)
VALUES (1, 'in_transit', now(), 'carrier');

    INSERT 0 1.

    The control. A trigger that blocked everything would satisfy both steps above and quietly break the feature.

  5. Try an event status that does not exist.

    INSERT INTO shipment_events (shipment_id, status, occurred_at, source)
VALUES (1, 'eaten_by_dog', now(), 'admin');

    ERROR: new row … violates check constraint "ck_shipment_events_status_valid"

  6. And the constraint a dispute depends on — a carrier shipment with no tracking number. 

    INSERT INTO shipments (order_id, method, carrier, dispatched_at)
VALUES (999999, 'carrier', 'usps', now());

    Refused by ck_shipments_method_requires_tracking (or the foreign key, if order 999999 does not exist — use a real order id without a shipment to see the right one).

    That row is exactly what a payment processor asks for during a “not received” dispute. Left optional, the field ends up empty precisely on the orders where it matters.

  7. Leave, and tidy up the extra event you inserted.

    ALTER TABLE shipment_events DISABLE TRIGGER shipment_events_no_update_delete;
DELETE FROM shipment_events WHERE status = 'in_transit' AND source = 'carrier';
ALTER TABLE shipment_events ENABLE TRIGGER shipment_events_no_update_delete;
\q

    Needing to disable the trigger to clean up is the guard proving itself one last time.

05

Record what failed

Anything that surprised you is worth writing down while it is fresh.

  1. Add anything that behaved unexpectedly to docs/defect-log.md, newest first.

    Twenty entries so far, and almost none came from a test failing — the suite was green throughout. They came from reading code, using the store, and breaking guards on purpose to watch a test fail.

  2. Note anything the documents got wrong, not just the code.

    A verification step vague enough to be read two ways is its own defect, and there is already a section of the log for exactly that.
