Manitou Reference · Store config · Brand

Wordmark
& Logo

The masthead is one config field away from being a different store's. Set store.name and it renders as text in the display face; set store.logo and it renders your artwork instead. Neither is a placeholder for the other — the header, the footer and the vendor portal all read the same two values through one component. Every measurement below was taken in a browser, not estimated.

01

A different name

No artwork needed. This is the intended path for most clones, and it produces a finished-looking masthead on its own. 

// store-config.json  (repo root)
"store": {
  "name": "Ridgeline",
  "logo": "",
  "support_email": "support@ridgeline.example",
  "tagline": "..."
}
cd web && npm run tokens

store-config.json is the source; web/lib/store-config.ts is generated from it and is git-ignored. Editing the generated file is editing something the next build overwrites.

How the text is set

Face
Archivo Black — typography.fontFamily.display
Size
18px, line-height 1.5 — text-lg
Case
Uppercase, applied in CSS. Type the name normally in config.
Tracking
-0.025em — tracking-tight
Colour
#1C1917 — color.text
Ink height
13px cap height at this size

How long a name can be

The masthead does not shrink or wrap — it is shrink-0 — so a long name pushes the page sideways on a phone rather than compressing. Measured in Chrome at a 375px viewport:

NameCharactersRendered widthAt 375px
Manitou792.2pxfits
Ridgeline9106.0pxfits
Ember & Ash11136.0pxfits
Northbay Co11142.0pxfits
Northbay Provisions19234.3pxoverflows by 84px
Roughly 11 characters, including spaces. Archivo Black is a wide face — about 13px per character at 18px — so the limit arrives sooner than it looks. A longer trading name goes in store.tagline or in the footer; the masthead takes the short form. If the full name must appear, that is the case for artwork: a two-line lockup fits horizontally where one line cannot.
02

An SVG logo

Three steps, no code change.

1. Put the file in web/public/          →  web/public/logo.svg
2. Point store-config.json at it       →  "logo": "/logo.svg"
3. Regenerate                          →  cd web && npm run tokens

The path is the served path, not the path on disk. Everything in web/public/ is served from the site root, so web/public/logo.svg is /logo.svg.

Accepted

"logo": "/logo.svg"
"logo": "/brand/wordmark.svg"
"logo": "https://cdn.example/logo.svg"

A root-relative path, or an absolute URL — the second is there for Phase 6, if assets move behind CloudFront.

Refused at startup

"logo": "logo.svg"
"logo": "./logo.svg"
"logo": "public/logo.svg"

None of these resolve from a nested route like /products/tee. The API refuses to boot rather than let it through.

ValidationError: store.logo must be a public path like /logo.svg
(got 'logo.svg'). Put the file in web/public and reference it from the root.
Why refuse to start over a logo? Because a broken src is the quietest failure on the page. Nothing raises, nothing logs, no build fails: the header renders, the alt text stands in, and the store simply looks unfinished with nothing saying why. Better to stop while whoever just edited the config is still watching.

Setting "logo": "" returns to the text wordmark. That is a supported state, not a broken one — no code change either direction.

03

Size & ratio

The height is fixed and the width follows the artwork. So the only spec that constrains you is how wide the mark may be, and the phone decides it.

Rendered height
20px, always — h-5 w-auto in components/ui/wordmark.tsx
Width
Intrinsic. Whatever your viewBox ratio makes it at 20px tall.
Recommended max width
126px  (6.3 : 1)
Hard limit
150px  (7.5 : 1) — 151px scrolls the page sideways
Minimum
None, but under ~60px a wordmark stops being legible at 20px tall
For reference
The text "Manitou" occupies 92.2px — 4.6 : 1

Where those numbers come from

A 375px viewport is the narrowest the storefront is designed for, and the header packs the most into one row there. Drawn at actual size — these bars are 375 real pixels wide:

180px — 30px past the edge, and the right-hand gutter is gone entirely. The whole page scrolls sideways, on every screen of the site.

Verified by stepping a probe SVG through 126, 140, 150, 151, 155, 160, 170 and 180px and reading document.documentElement.scrollWidth each time. 150 fits; 151 overflows by exactly 1px, and the overflow grows 1:1 from there. The same 150px budget applies to the text wordmark — "Northbay Provisions" at 234.3px overflowed by 84px, which is 234.3 − 150.

Wider screens are not the constraint. At 769px the budget is 228px and at 1280px it is 611px, because the category nav takes the slack rather than the mark. Design to 375px and every other width is free.

One thing that will surprise you

The text wordmark is 18px type but only 13px of actual ink — the rest of the line box is empty. Artwork trimmed tight to its shapes renders the full 20px, so a logo swapped in for the text reads about half again as large.

That is usually right: a logo is meant to have more presence than a line of type. If you want it to sit at the same optical weight as the text it replaced, add breathing room inside the viewBox rather than changing the class — a mark with ~3px of padding top and bottom in a 20-unit box lands at 13-14px of ink.

04

Colour

The colour has to be inside the file. This is the part that catches people.

currentColor does not work here. An SVG loaded through <img src> is a separate document. It cannot see the page's CSS, its color, or any Tailwind class — the same isolation that makes <img> safe to point at untrusted files. fill="currentColor" falls back to the browser's default text colour, which is plain black. Against #1C1917 that looks almost right, which is exactly what makes it worth calling out: it will not look broken, it will just quietly stop matching the day the token changes.
Fill
#1C1917 — color.text, the same value the text wordmark uses
Sits on
#FFFFFF — color.surface, in the header, the footer and the portal nav
Colours
One, unless the brand genuinely needs more. A single-fill mark is a smaller file and stays legible at 20px.
Dark theme
None today, so one file is enough

If a dark theme ever arrives, an <img> cannot adapt and there are two honest fixes: inline the SVG as a React component so it inherits currentColor, or ship two files and pick between them with <picture>. Both are changes to wordmark.tsx, not to config — which is the right place for that decision to live.

Hardcoding #1C1917 inside an artwork file is not a breach of the "never hardcode a colour" rule. That rule governs components, which must read design-tokens.json. An SVG is an asset, like a product photo — but note the value here so that if color.text ever changes, the logo is on the list of things to re-export.
05

Preparing the file

What to check before the file goes in web/public/.

CheckWhy
Text converted to paths The most important one. A <text> element naming a font renders in whatever the viewer's machine substitutes. Outline it in the design tool before exporting.
viewBox present Without it the browser cannot compute a width from the fixed height, and w-auto has nothing to work from.
xmlns present Required when an SVG is loaded as an image rather than inlined. Most exporters include it; hand-edited files often lose it.
Trimmed to the artwork Stray whitespace in the viewBox becomes invisible padding, so the mark renders smaller than 20px and sits off-centre.
No width/height attributes Harmless — the CSS classes win — but they suggest a size the page ignores. Drop them so the file does not mislead the next person.
No <script>, no external references An <img> will not run scripts or fetch external resources, so anything relying on them silently does not render.
No embedded raster A PNG inside an SVG is a PNG: it is not scalable and it is not small. If the mark cannot be vector, use a real PNG.
Under ~4KB A one-colour wordmark should be 1-2KB. Much more means the exporter left editor metadata behind.

A minimal, correct file

<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 116 20">
  <path fill="#1C1917" d="M4 2h6l4 11 4-11h6v16h-4V8l-4 10h-4L8 8v10H4z"/>
</svg>

116 by 20 — a 5.8 : 1 mark, inside the recommended budget. One fill, one path, no metadata, no font dependency.

PNG, and why not JPG

PNG is the fallback if the mark cannot be vector — a photographic texture, a gradient mesh. Export at 3× (60px tall) so it stays sharp on high-density screens, and keep transparency.

Never JPG. It has no transparency, so the mark arrives in a box of near-white that will not match the header, and its compression puts visible haloes exactly where a logo has hard edges against a flat background.

Before you commit

# regenerate the config the app reads
cd web && npm run tokens

# the path is validated here -- a bad one fails these
cd ../backend && .venv/bin/python -m pytest tests/test_store_identity.py

# and the app still compiles
cd ../web && npx tsc --noEmit

Then look at it, which is the part no test covers:

  • Load / — header and footer both show the mark.
  • Load /admin — the portal masthead matches the storefront.
  • Narrow the window to 375px and confirm the page does not scroll sideways. This is the check that catches an oversized mark, and the only one that does.
  • Check the tab title and the home hero still read correctly — those follow store.name, not the artwork.
Commit the source, not the output. store-config.json and the file in web/public/ are tracked. web/lib/store-config.ts is generated by npm run tokens and is git-ignored — if it shows up in git status, something has gone wrong with the ignore rules rather than with your change.
