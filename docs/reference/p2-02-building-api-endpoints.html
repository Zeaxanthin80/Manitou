00

The request cycle

Everything in Phase 2 is one of the steps below. When a piece of code confuses you, the first useful question is "which step is this?" 

  Browser / app                         FastAPI                    PostgreSQL
      │                                    │                             │
      │  GET /products?limit=20            │                             │
      ├───────────────────────────────────▶│                             │
      │                                    │                             │
      │                   1. ROUTE   match URL to a Python function      │
      │                   2. VALIDATE parse + check inputs (Pydantic)    │
      │                   3. AUTH     run any Depends() checks           │
      │                                    │                             │
      │                   4. QUERY    build SQL via SQLAlchemy           │
      │                                    ├────────────────────────────▶│
      │                                    │◀────────────────────────────┤
      │                                    │  rows → Python objects      │
      │                                    │                             │
      │                   5. SERIALISE objects → JSON (Pydantic)         │
      │                   6. STATUS    attach 200 / 404 / 422            │

      │◀───────────────────────────────────┤                             │

Six steps, and each has exactly one job. The overwhelm comes from meeting all six in one file for the first time — not from any single one being hard.

01

What an endpoint is

An endpoint is one URL paired with one HTTP method, handled by one Python function. That's the whole definition. 

@router.get("/products")              # ← this line makes it an endpoint
async def list_products():
    return [...]

The decorator tells FastAPI: "when a GET request arrives for /products, call this function." Nothing more mysterious than that.

Methods carry meaning

REST conventions assign each HTTP method a job. Following them means any client developer can predict your API without reading docs.

Method Means Manitou example
GET Read. Never changes anything. GET /products
POST Create something new. POST /auth/register
PATCH Update part of something. PATCH /admin/products/5
PUT Replace something entirely. Rarely needed; PATCH usually fits better.
DELETE Remove something. DELETE /cart/items/3
The rule that makes GET special

A GET must never change data. Browsers, proxies, and CDNs all assume this — they'll pre-fetch, cache, and retry GETs freely. An endpoint like GET /products/5/delete is a genuine hazard: a crawler following links would start deleting your catalogue.

Resources, not actions

URLs name things (nouns); methods supply the verb. This is the single biggest shift if you're used to thinking in function names.

Action-style (avoid) Resource-style (correct)
GET /getAllProducts GET /products
POST /createProduct POST /products
GET /getProductById?id=5 GET /products/5
POST /deleteProduct DELETE /products/5
02

URL anatomy

Two ways to pass information in a URL, and they are not interchangeable. Choosing wrongly is one of the most common early API mistakes.

https://api.manitou.example/products/classic-cotton-tee?include=variants&limit=20

Resource path

Which collection. Plural noun, always. /products, /categories, /orders.

Path parameter

Identifies one specific thing. Required — without it the URL means something different. Declared as /products/{slug}.

Query parameters

Modifies how you view the collection. Always optional, always has a sensible default. Filtering, sorting, paging.

The test: if removing it would change which thing you're asking for, it's a path parameter. If removing it just gives you a broader or default view of the same thing, it's a query parameter.

URL Reading
/products All products, default view
/products/classic-cotton-tee One specific product
/products?category=t-shirts All products, filtered view
/products?limit=20&offset=40 All products, third page of 20
/categories/t-shirts/products Products belonging to one category — a nested resource

In FastAPI the distinction is automatic: a name that appears in the route string becomes a path parameter, and any other function argument becomes a query parameter. 

@router.get("/products/{slug}")
async def get_product(
    slug: str,                       # in the path → path parameter
    include_variants: bool = True,   # not in path → query parameter, optional
):
03

Status codes

A three-digit number telling the client what happened, before it reads a single byte of the body. Clients branch on this, so getting it right is functional, not cosmetic.

Code Name When Manitou returns it
200 OK Successful GET, PATCH, or DELETE. The default success.
201 Created A POST made something new — registration, an order.
204 No Content Succeeded, nothing to return. Common for DELETE.
400 Bad Request Malformed in a way validation didn't cover.
401 Unauthorized Not authenticated — missing or invalid token.
403 Forbidden Authenticated, but the role isn't permitted.
404 Not Found That slug or id doesn't exist.
409 Conflict Clashes with existing state — duplicate email, duplicate slug.
422 Unprocessable FastAPI's automatic validation failure. Wrong type, missing required field, failed constraint.
500 Server Error Your code crashed. Always a bug, never the client's fault.
The 4xx / 5xx split

4xx means the client did something wrong — bad input, missing auth, asking for something absent. 5xx means the server did something wrong. If a malformed request produces a 500, that's a bug in your error handling: it should have been a 400 or 422.

404 vs 200 with an empty list

This trips people up constantly, and the rule is clean:

GET /products/no-such-slug → 404. You asked for one specific thing; it doesn't exist.
GET /products?category=empty-cat → 200 with []. You asked for a collection matching a filter; the collection is legitimately empty. An empty result is not an error.

Your Apparel category from the SQL exercises is exactly this case — it has no products, and asking for them is a successful request that returns nothing.

04

Slugs

A URL-safe text identifier: lowercase, words joined by hyphens, no spaces or punctuation. You already have them — classic-cotton-tee, t-shirts. 

Product name:  "Classic Cotton Tee"
Slug:          "classic-cotton-tee"

  /products/5                     ← works, tells nobody anything
  /products/classic-cotton-tee    ← works, and is readable

Why they exist

Readability A person can tell what the link points at before clicking.
SEO Search engines weigh words in URLs. For a store, this is a real commercial reason — and part of why Section 3 chose Next.js for server rendering.
Stability Database ids are an internal implementation detail. Slugs are a deliberate public contract.
No enumeration Sequential ids let anyone walk /products/1, 2, 3 and count your catalogue. Slugs don't invite that.
The trap: slugs are mutable, ids are not

If the owner renames "Classic Cotton Tee" to "Classic Tee," should the slug change? If yes, every existing link and bookmark breaks. If no, the slug slowly stops matching the name.

The usual answer: generate the slug once at creation, then leave it alone. Renaming the product does not regenerate it. If a slug genuinely must change, keep the old one as a redirect. This is a real decision for Phase 4's product editor — worth settling deliberately rather than discovering later.

Note your schema already enforces this properly: products.slug carries a unique constraint from Section 6.5, so two products can never collide on one. When generating slugs from names, that collision is a real case to handle — two products called "Tote Bag" need tote-bag and tote-bag-2.

05

The three layers

The folder structure from Section 4 of PROJECT_PLAN.md isn't arbitrary. Each layer has one job, and knowing which layer you're in tells you what belongs there.

HTTP

Router

app/routers/products.py

Owns URLs, methods, status codes, and auth dependencies. Should be thin — it translates HTTP into a function call and translates the result back. No business rules, no SQL.

LOGIC

Service

app/services/products.py

Owns the actual work: querying, filtering, calculating. Knows nothing about HTTP — no status codes, no request objects. This is what makes checkout testable in isolation later.

DATA

Model

app/models/product.py

The SQLAlchemy classes mapping to tables. Structure and relationships only — the tables you already inspected with \d products.

CONTRACT

Schema

app/schemas/product.py

Pydantic classes defining what the API accepts and returns. Sits alongside the others rather than under them — see section 06.

A practical way to use this

When Claude Code produces a file and you're lost, ask "which layer is this, and what's its one job?" A router file doing SQL, or a service raising HTTPException, is a sign the layers have bled together — which is worth pushing back on, because that's exactly what makes code hard to follow.

06

Models vs schemas

The distinction that confuses almost everyone at this point: you now have two classes that both look like "a product."

SQLAlchemy model Pydantic schema
Describes A database table A JSON shape
Lives in models/ schemas/
Job Read and write rows Validate input, shape output
Contains Every column Only fields the API should expose

They're separate on purpose. The model has columns the outside world must never see — most obviously users.password_hash. If your endpoint returned model objects directly, that hash would go out over the wire. The schema is what stops it, structurally rather than by remembering. 

# schemas/product.py
class ProductOut(BaseModel):
    id: int
    name: str
    slug: str
    base_price: Decimal
    # description, is_active, created_at deliberately omitted

    model_config = ConfigDict(from_attributes=True)  # read from ORM objects

Declaring response_model=ProductOut on the route makes FastAPI enforce it: anything not in the schema is stripped from the response, whether you remembered or not. It also documents itself in /docs automatically.

Why there are usually three schemas per resource

ProductCreate (what a POST accepts), ProductUpdate (what a PATCH accepts — all fields optional), and ProductOut (what gets returned). They differ genuinely: a client must not send id or created_at, but the response should include them.

07

How relationships load

Your model says a product has variants. The question SQLAlchemy has to answer is when to fetch them — and the default answer causes the problem in the next section. 

# This line does not run a query. It defines a relationship.
class Product(Base):
    variants = relationship("ProductVariant", back_populates="product")

By default this is lazy: the variants are fetched only when you first touch product.variants, in a separate query, at that moment. Convenient in a script; disastrous in a loop.

Strategy Behaviour Use when
lazy (default) One extra query, on first access, per parent object. You touch a single object and might not need the relationship at all.
selectinload Two queries total: parents, then all children in one WHERE id IN (...). The usual right answer for lists — clean and predictable.
joinedload One query with a JOIN; parent columns repeat per child row. Fetching one object with a small related set. Wasteful across a big list.
08

The N+1 problem

The most common performance bug in ORM code, and the one Claude Code was almost certainly guarding against. The code looks completely innocent. 

products = session.query(Product).all()        # 1 query
for p in products:
    print(p.variants)                          # 1 query — EACH TIME ROUND
WITHOUT eager loading — your 3 seeded products

  SELECT * FROM products;                                  ← 1
    SELECT * FROM product_variants WHERE product_id = 1;   ← +1
    SELECT * FROM product_variants WHERE product_id = 2;   ← +1
    SELECT * FROM product_variants WHERE product_id = 3;   ← +1
                                                    total: 4 queries

  With 200 products:                               total: 201 queries
  ────────────────────────────────────────────────────────────────────
WITH selectinload(Product.variants)

  SELECT * FROM products;                                  ← 1
  SELECT * FROM product_variants WHERE product_id IN (1,2,3);  ← 1
                                                    total: 2 queries

  With 200 products:                                 total: 2 queries

"N+1" is literal: one query for the parents, plus N more — one per parent. The fix is to tell SQLAlchemy up front that you'll need the children: 

from sqlalchemy.orm import selectinload

products = session.scalars(
    select(Product).options(selectinload(Product.variants))
).all()
Why it hides so well

Nothing errors. Nothing looks wrong. With your 3 seeded products it's 4 queries instead of 2 — imperceptible. The bug only surfaces in production with a real catalogue, as a page that mysteriously takes four seconds.

This is the tradeoff of an ORM, stated plainly: it hides SQL so well that you can write hundreds of queries without noticing. That's exactly why turning on echo=True and watching the SQL is worth doing early.

Try it yourself

Set echo=True on your engine, hit the product-list endpoint, and count the SELECT statements in your terminal. Then add selectinload and count again. Seeing 4 drop to 2 makes this concrete in a way no explanation does.

09

Pagination and filtering

A product list endpoint must never return the whole table. With 3 rows that feels absurd; the habit is what matters. 

GET /products?limit=20&offset=40&category=t-shirts&sort=price_asc
limit How many rows. Always give it a default and a maximum — otherwise ?limit=1000000 is a free denial-of-service.
offset How many to skip. Page 3 of 20 is offset=40.
category Optional filter. Absent means no filtering, not an error.
sort Validate against a fixed allowed list — never interpolate it into SQL.

Return the total alongside the page, so a client can render "page 3 of 12" without guessing: 

{
  "items": [ ... 20 products ... ],
  "total": 237,
  "limit": 20,
  "offset": 40
}
ORDER BY is not optional here

From the SQL exercises: without ORDER BY, PostgreSQL makes no guarantee about row order. With pagination that becomes a visible bug — the same product can appear on page 1 and page 2, while another never appears at all. Any paginated query needs a deterministic sort, ideally ending in a unique tiebreaker like id.

10

CTEs — and whether you need one

A Common Table Expression is a named temporary result set defined at the top of a query with WITH. Two distinct uses, and only one of them is advanced. 

WITH low_stock AS (
    SELECT variant_id, quantity_available
    FROM inventory
    WHERE quantity_available < 10
)
SELECT v.sku, l.quantity_available
FROM low_stock l
JOIN product_variants v ON v.id = l.variant_id;

That's the plain use: a named subquery, purely for readability. It does nothing a nested subquery couldn't, it just reads better when a query gets long.

Recursive CTEs — the actually-advanced version

A WITH RECURSIVE CTE can walk a tree of unknown depth — the tool for "give me this category and every descendant, however deep the nesting goes." That's a genuine capability plain SQL lacks, and it's why CTEs get raised alongside category hierarchies.

Push back on this one

Your category tree is three rows, two levels deep: Apparel, with T-Shirts and Accessories beneath it. Recursion solves a problem you do not have.

A recursive CTE for that is exactly the "generalize ahead of need" pattern CLAUDE.md rules out. A plain self-join — exercise 18 in your SQL workbook, which you have already written — returns the same result and is code you can read.

Worth asking Claude Code directly: "Given we have 3 categories and 2 levels, is a recursive CTE necessary for step 2, or does a self-join cover it?" If the honest answer is that recursion is for arbitrary depth we don't have, that's a chunk of complexity you can drop today and add the day a store actually needs five-level nesting.

Not knowing CTEs is not blocking you. They're a query-readability tool, and the recursive form solves a structural problem your data doesn't currently have. File it under "understood, deferred."

11

A worked endpoint

Every concept above, in one small function. Read it once now; it'll make more sense after you've written your own. 

# app/routers/products.py

@router.get(
    "/products/{slug}",          # ← §02 path parameter
    response_model=ProductOut,      # ← §06 output contract
)
async def get_product(
    slug: str,                      # ← path param, required
    session: Session = Depends(get_session),
):
    product = products_service.get_by_slug(session, slug)   # ← §05 thin router

    if product is None:
        raise HTTPException(404, "Product not found")   # ← §03 one thing, absent

    return product          # ← §06 Pydantic strips anything not in ProductOut


# app/services/products.py — knows nothing about HTTP

def get_by_slug(session: Session, slug: str) -> Product | None:
    stmt = (
        select(Product)
        .where(Product.slug == slug, Product.is_active.is_(True))
        .options(selectinload(Product.variants))    # ← §08 avoids N+1
    )
    return session.scalars(stmt).first()

Eleven lines of router, six of service. The router speaks HTTP and nothing else; the service speaks the database and nothing else. Every concept in this document appears exactly once.

How to work through step 2

Build one endpoint end to end before starting the next. Get GET /products/{slug} working, test it in /docs, and understand every line of it. The second endpoint reuses 80% of the same shapes, and the fifth is nearly mechanical.

Trying to understand all of step 2 at once is what makes it feel impossible. Trying to understand one endpoint is a normal afternoon.

Glossary

Endpoint One URL + one HTTP method, handled by one function.
Route / path operation FastAPI's terms for the same thing.
Router A group of related endpoints in one file.
REST Representational State Transfer — the convention of URLs as nouns and HTTP methods as verbs.
Resource A thing the API exposes: a product, an order, a category.
Path parameter Required value inside the URL path, identifying one specific thing.
Query parameter Optional value after ?, modifying the view.
Slug Lowercase hyphenated URL-safe identifier.
Serialisation Turning Python objects into JSON.
Schema (Pydantic) A class defining an accepted or returned JSON shape.
Model (SQLAlchemy) A class mapping to a database table.
ORM Object-Relational Mapper — SQLAlchemy, translating objects to SQL.
Lazy loading Fetching a relationship only when first accessed.
Eager loading Fetching a relationship up front, deliberately.
N+1 problem One query for parents plus one per parent, from lazy loading in a loop.
selectinload / joinedload SQLAlchemy's two main eager-loading strategies.
Pagination Returning a bounded slice of a collection.
CTE Common Table Expression — a named temporary result set via WITH.
Recursive CTE A CTE that references itself, for walking trees of unknown depth.
Dependency injection FastAPI's Depends() — declaring what a route needs and letting the framework supply it.
Idempotent Repeating the request has the same effect as doing it once. GET, PUT, and DELETE should be; POST usually isn't.
