Before you start

Three services, two accounts. The rest of this document assumes all of them.

Decide about the data first. The development database has accumulated test accounts from building this phase — several already-anonymised deleted-N@invalid rows among them. You can walk through as-is, or re-seed for a clean run. Re-seeding wipes the audit trail, which is fine here: this walkthrough rebuilds it. What you must not do is re-seed halfway through and wonder why the log is empty.

  1. Start PostgreSQL.

    docker compose up -d

    db running. Check with docker compose ps.

  2. Start the API in a terminal you can see — the password reset link is printed there. 

    cd backend
source .venv/bin/activate
uvicorn app.main:app --reload

    http://localhost:8000/health returns {"status":"ok"}.

  3. Start the web app.

    cd web
npm run dev

    http://localhost:3000 shows the storefront.

  4. Optional — reset to clean data. Skip if you would rather keep the existing accounts. 

    cd backend && source .venv/bin/activate
python seed.py

    Seeded products and two accounts: admin@manitou.example / admin and customer@manitou.example / customer.

  5. Have an authenticator app ready on your phone (Google Authenticator, 1Password, Aegis, anything TOTP).

    Needed for the two-factor steps. There is no way to fake this — that is the point of the feature.

01

Administrator — in the browser

Sign in as admin@manitou.example / admin. Items marked task 12 come straight from the plan.

Getting in

  1. Sign in as the admin, then open the avatar menu in the header.

    A Vendor portal link in accent red, above Your account. It does not appear for customers.

  2. /admin Open the portal.

    The VENDOR PORTAL badge, and six nav sections: Summary, Orders, Products, Inventory, Users, Audit.

  3. In a private window, sign in as customer@manitou.example and visit /admin.

    A 404, not an "access denied". 403 would confirm the page exists.

  4. Sign out entirely and visit /admin.

    Redirected to /login — they might be an admin, so they are asked.

Orders

  1. /admin/orders Filter by each status along the top.

    Counts change; the count in the heading matches the rows shown.

  2. Open a pending order and advance it: Mark paid → Mark shipped → Mark delivered.

    The buttons change at each step. After delivered there are none, and it says the order reached a final status.

  3. Check the customer's own view: sign in as that customer and open the same order.

    The status matches, and the line items show the price as charged, not today's price.

Products and stock

  1. /admin/products/new Create a product with one variant.

    Redirected to its edit page; it appears on the storefront immediately.

  2. Add a second variant, then add an image by URL.

    Try /product-placeholder.png. The first image becomes primary automatically.

  3. Add a second image and press Make primary.

    The badge moves. Only ever one primary — the database enforces it.

  4. Try to create another product with the same slug.

    A readable "Duplicate product slug" message, not a server error.

  5. Hide a product that has already been ordered, then find that old order.

    Gone from the storefront, still listed in the portal marked Hidden, and the past receipt still shows it.

  6. /admin/inventory Set a variant's stock below its reorder level.

    It flips to Reorder and jumps to the top of the list. At 0 it reads Out of stock and the storefront shows Sold out.

  7. Enter -1 as a stock level.

    Refused with a readable message.

Summary

  1. /admin Compare Revenue against Orders by status.

    Revenue counts paid, shipped and delivered only. Cancelled orders are excluded and pending is shown separately as Awaiting payment.

  2. Cancel an order, then reload the summary.

    Revenue does not rise. The cancelled row's value does.

Users — the guards

  1. /admin/users Search by name, then filter Customers / Admins / Suspended.

    Admins appear in the list. A list that hid them could never show who has access.

  2. Open your own row.

    Only Send password reset. No suspend, no anonymise, no role change — you cannot lock yourself out, and the buttons simply are not there.

  3. Open another customer's row.

    Suspend, Make admin, Send password reset and Anonymise all present.

  4. Promote a customer to admin, then open their row again.

    Now says Remove admin. With two admins you can demote either — the guard counts, it does not blanket-refuse.

Suspension task 12

  1. In a separate private window, sign in as a test customer and leave /account open.

    Use a private window, not another tab — same-browser tabs share one cookie jar and you would only be watching your own session.

  2. As the admin, suspend that customer. Then in the private window, click any link.

    Signed out on the next request — not when their token expires. The storefront still renders; no error page.

  3. Have them try to sign in again with the correct password.

    "This account has been suspended. Contact support@…" — and with a wrong password, the ordinary "Incorrect email or password". The difference matters: the second stops the first becoming a way to probe who is suspended.

  4. Reactivate them and confirm they can sign in.

    Back to normal, same password.

Reset, two-factor, anonymise

  1. Press Send password reset on a customer.

    Confirmation naming their address. The link is printed in the API terminal — you never see or set their password.

  2. Press it again immediately.

    Refused — one link a minute, so this cannot be used to bombard someone's inbox.

  3. On a customer who has two-factor on, press Turn off two-factor.

    The button disappears afterwards and the sidebar reads Two-factor: Off. This is the escape hatch for someone who lost their phone and their recovery codes.

  4. Open Anonymise this account on a test customer and try to arm it: password alone, then password plus a wrong email.

    Disabled both times. Only the exact address arms it — the mistake worth preventing here is erasing the wrong row.

  5. Anonymise them properly, then find their old order.

    Row becomes deleted-N@invalid / "Deleted account". The order survives with its shipping address — that is the despatch record, and tax rules require keeping it.

Audit task 12

  1. /admin/audit Find every action you just performed.

    customer.suspended, customer.reactivated, customer.role_changed, customer.password_reset_sent, customer.2fa_disabled, customer.anonymised, plus the product, inventory and order events. Each names you as the actor.

  2. Use the action filter, then clear it.

    The dropdown keeps offering every action even while filtered.

  3. Look for any way to edit or delete an entry.

    There is none, on this page or anywhere else. The table is append-only in the database; section 02 proves it.

  4. Open a user's detail page and read their History section.

    Only that account's events, newest first.

02

Administrator — from the terminal

Four checks the browser cannot make. Every command below has been run against this project — the expected output is the real output, not an approximation.

  1. Find a reset link in the API terminal. task 12

    A boxed banner. If you redirected uvicorn to a file, grep it instead: 

    grep -A6 "EMAIL (console sender" your-api-log
┌─ EMAIL (console sender — not actually sent) ──────
│ To:      customer@manitou.example
│ Subject: Reset your Manitou password
│ http://localhost:3000/reset-password?token=…

  2. Prove the audit trail refuses UPDATE. task 12 

    docker compose exec db psql -U manitou -d manitou \
  -c "UPDATE audit_events SET action='tampered' WHERE id=(SELECT min(id) FROM audit_events);"
ERROR:  audit_events is append-only; UPDATE is not permitted

    That exact error, and 0 rows changed. You are connecting as the application's own database user — this is not a permissions trick.

  3. Prove it refuses DELETE. task 12 

    docker compose exec db psql -U manitou -d manitou \
  -c "DELETE FROM audit_events WHERE id=(SELECT min(id) FROM audit_events);"
ERROR:  audit_events is append-only; DELETE is not permitted

    Both refused by a database trigger, not by application code — so a bug in the API cannot rewrite history.

  4. Confirm an anonymised row is genuinely scrubbed.

    docker compose exec db psql -U manitou -d manitou \
  -c "SELECT id, email, full_name, is_active FROM users WHERE email LIKE 'deleted-%' ORDER BY id DESC LIMIT 3;"
 id  |        email        |    full_name    | is_active
-----+---------------------+-----------------+-----------
 206 | deleted-206@invalid | Deleted account | f

    No real name, no real address, sign-in disabled. .invalid is a reserved suffix — it can never be a deliverable address.

  5. Confirm the audit records who erased an account, and that a customer erasing themselves is not re-identified by the log. 

    docker compose exec db psql -U manitou -d manitou \
  -c "SELECT actor_email, details->>'initiated_by' AS by FROM audit_events WHERE action='customer.anonymised' ORDER BY id DESC LIMIT 4;"
      actor_email      |  by
-----------------------+-------
 admin@manitou.example | admin
 deleted-199@invalid   | self

    Admin-initiated names the admin. Self-initiated shows the already scrubbed address — writing their real one into an append-only table would undo the erasure they just asked for.

  6. Run the automated suite once.

    cd backend && source .venv/bin/activate
python -m pytest

    99 passed

03

Beta customer — in the browser

Do this as a real shopper would, in a private window, with an address you can actually receive at — you will need to read a reset link. A fresh registration is better than the seeded account: it exercises the path a real customer takes.

Shopping

  1. /register Create an account.

    Signed in immediately, no second form. Try a password under 8 characters first — it should be refused.

  2. Browse the catalogue and each category from the nav.

    Prices shown; multi-variant products read From $X.

  3. Open a product and try to add it without choosing a size.

    The button says Select an option and is disabled. A sold-out variant cannot be selected.

  4. Add two different items, then add the same one twice.

    The repeat merges into one line with quantity 2 — it does not create a second line. Header count updates.

  5. /cart Change a quantity, then remove a line.

    Subtotal follows both changes.

  6. Check out. You have no saved address, so add one.

    The address form appears automatically. After saving, it is selectable and "Billing same as delivery" is pre-ticked.

  7. Place the order.

    A receipt with an order number, the items, and the address. Cart now empty; nothing was charged — payments arrive in Phase 5.

  8. /orders Find the order, then try changing the number in the URL to someone else's.

    Yours renders. Another's gives 404 — not "403", which would confirm it exists.

Account

  1. /account Change your name, leaving Phone blank.

    Name updates in the header. If you had a phone number saved, it is still there — an untouched field is not wiped.

  2. Add a second address, then remove it.

    Removes cleanly. Now try removing the address used by your order — refused, because it is part of the despatch record.

Password and sessions

  1. Sign in on a second device or private window and leave it open.

    Two live sessions.

  2. /account/security Change your password. Try a wrong current password first.

    Wrong one refused. After success, this window stays signed in.

  3. Now click something in the other window.

    Signed out. That is the point — after a compromise, changing your password ends every other session while keeping the one you are using.

  4. Change your email address.

    A notice sent to your previous address (check the API terminal). You now sign in with the new one.

Forgotten password task 12

  1. Sign out. /forgot-password Request a link for an address that does not exist, then for yours.

    Identical wording both times. The page must not reveal which addresses have accounts.

  2. Take the link from the API terminal and set a new password.

    Returned to sign-in with a confirmation banner. You are not auto-signed-in — a link in an inbox should never produce a live session.

  3. Open the same link a second time.

    Refused. One use only, and it expires after 30 minutes.

  4. Sign in with the new password.

    Works; the old one does not.

Two-factor task 12

  1. /account/security Set up two-factor and scan the QR with your authenticator.

    A QR code plus a typed secret for apps that cannot scan.

  2. Before entering a code, sign out and back in.

    No code asked for. An abandoned setup must not lock you out — only finishing it turns two-factor on.

  3. Finish setup: enter a wrong code, then the real one.

    Wrong one refused. Then ten recovery codes, shown once. Write them down — they are hashed and cannot be shown again.

  4. Sign out and sign in again.

    Password, then a second screen asking for a code. Your password alone reaches nothing.

  5. Enter the code your app is showing — if you just used it to enable, wait for the next one.

    Signed in. A code already used is refused even while still on screen, which is why you may need to wait 30 seconds.

  6. Sign out, sign in, and use a recovery code instead. task 12

    Signed in. Try the same code again — refused; each works once. Another one still works.

  7. Turn two-factor off, using your password.

    Sign-in stops asking for a code. Your password, not a code — the usual reason to turn it off is that the authenticator is gone.

Closing the account

  1. /account/security Open Close my account and try to arm it with the password alone, then with lowercase delete.

    Disabled both times. Only password plus DELETE in capitals arms it.

  2. Close the account.

    Returned to the storefront, signed out. Your old credentials no longer work, and /account sends you to sign in.

  3. As the admin, find that order in the portal.

    The order is still there with its total and address, attributed to a deleted account. Receipts survive; the person does not.

04

Beta customer — quality floor

Section 4.3 calls these non-negotiable on every screen. Check them on at least the home page, a product page, the cart, checkout and /account/security.

  1. Narrow the window to about 375px, or use a phone.

    No sideways scrolling anywhere. The nav collapses to a hamburger; the cart and avatar stay in the header.

  2. Put the mouse away. Tab through a whole purchase.

    Every control reachable, and you can always see where you are. Esc closes the menus and returns focus to the button that opened them.

  3. Turn on "reduce motion" in your OS settings and reload.

    Nothing animates or slides.

  4. Check the images have alt text — browser reader mode, or right-click → Inspect.

    Descriptions of the product, not "image1.png".

  5. Read the footer and the suspension message.

    Store name, tagline and support address all present. These come from store-config.json, so a cloned store changes them in one file.

  6. Trigger an error on purpose — a wrong password, a duplicate email.

    Every message says what went wrong and what to do about it. No stack traces, no raw status codes.

  7. Empty your cart and visit /cart; visit /orders with no orders.

    Empty states invite an action ("Browse products"), rather than just reporting emptiness.
