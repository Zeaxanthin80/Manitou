Authentication

00

The problem

HTTP is stateless. Every request arrives at your server with no memory of any request before it. The server has no inherent idea that the request asking for /orders came from the same person who logged in thirty seconds ago.

That's not a flaw — it's what lets a server handle thousands of unrelated requests without tracking who's "connected." But it means identity must be re-proven on every single request.

The naïve fix is to send the email and password with every request. That's catastrophic: the password crosses the network hundreds of times per session, ends up in logs and browser history, and has to be held in memory by the client the whole time. The entire field of API authentication exists to avoid that.

The core idea

Prove who you are once, with the real credentials. Receive a token — a temporary, limited, revocable stand-in. Send the token, not the password, on everything after that.

01

AuthN vs AuthZ

Two words that look alike, get abbreviated alike, and mean different things. Manitou needs both.

Concept Question it answers In Manitou
Authentication (AuthN) Who are you? Verifying identity. Email + password checked against users.password_hash
Authorization (AuthZ) What are you allowed to do? Verifying permission. The role column — customer vs admin

A logged-in customer is authenticated but not authorized to reach the vendor portal. Both checks run on every protected request: first "is this token valid?", then "does this role permit this action?"

Phase 2 task 1 builds both — JWT issuing covers AuthN, the role check covers AuthZ. Phase 4's /admin gate is pure AuthZ layered on top.

02

The handshake

The full exchange, once at login and then on every request afterwards. 

STEP 1 — LOGIN (once per session)

  Client                                      API                        Database
    │                                          │                             │
    │  POST /auth/login                        │                             │
    │  { email, password }                     │                             │
    ├─────────────────────────────────────────▶│                             │
    │                                          │  SELECT ... WHERE email=?   │
    │                                          ├────────────────────────────▶│
    │                                          │◀────────────────────────────┤
    │                                          │  row with password_hash     │
    │                                          │                             │
    │                              bcrypt.checkpw(sent, stored)              │
    │                                          │                             │
    │                              sign JWT with server secret               │
    │  { access_token: "eyJ...",               │                             │
    │    token_type: "bearer" }                │                             │
    │◀─────────────────────────────────────────┤                             │

STEP 2 — EVERY REQUEST AFTERWARDS

  Client                                      API
    │                                          │
    │  GET /orders                             │
    │  Authorization: Bearer eyJ...            │
    ├─────────────────────────────────────────▶│
    │                            verify signature — no DB hit
    │                            read user_id + role from payload
    │                            check role permits this route
    │  200 OK  { orders: [...] }               │
    │◀─────────────────────────────────────────┤
Why this scales

Step 2 involves no database lookup to establish identity. The token is signed, so the server verifies it mathematically using its own secret. That's the central advantage of JWTs over server-side sessions — and also the source of their central drawback (see section 12).

03

JWT anatomy

A JSON Web Token is three Base64url-encoded segments joined by dots. It looks like noise; it isn't. Anyone can read it.

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxIiwicm9sZSI6ImFkbWluIiwiZXhwIjoxNzY3MjI1NjAwfQ.4pcPyMD09olPSyXnrXCjTwXyr4qJj1hFYXWvGCJhLPo

Header

Which algorithm signed this, and what type of token it is.

{
  "alg": "HS256",
  "typ": "JWT"
}

Payload (claims)

Who the user is and what they're permitted. Readable by anyone. 

{
  "sub": "1",
  "role": "admin",
  "exp": 1767225600
}

Signature

HMAC of the first two parts, using the server's secret. Proves nothing was altered. 

HMACSHA256(
  b64(header) + "." +
  b64(payload),
  JWT_SECRET
)
The most misunderstood point in this entire document

A JWT is signed, not encrypted. Base64 is encoding, not encryption — anyone holding the token can decode the payload and read every claim in it. Paste one into jwt.io and you'll see your own user_id and role in plain text.

What the signature guarantees is integrity, not secrecy: nobody can change "role": "customer" to "role": "admin", because they'd need JWT_SECRET to produce a matching signature. Never put anything confidential in a payload — no passwords, no card details, no personal data you wouldn't hand to the token's holder.

Standard claims worth knowing

sub Subject — who the token is about. Manitou puts users.id here.
exp Expiry — Unix timestamp after which the token must be rejected. Non-negotiable; always set it.
iat Issued at — when the token was created.
jti JWT ID — a unique identifier, used if you ever build a revocation blocklist.
role A custom claim. Not part of the spec — Manitou's own addition, driving the AuthZ check.

HS256 vs RS256

HS256 is symmetric: one secret both signs and verifies. Simple, fast, and correct when the same service does both — which is exactly Manitou's shape, one API issuing and verifying its own tokens. RS256 is asymmetric: a private key signs, a public key verifies. That matters when several independent services need to verify tokens without being trusted to issue them. Use HS256 here; reach for RS256 only if the architecture ever splits.

04

The Bearer scheme

How the token actually travels on each request. This part is standardised (RFC 6750) and identical for web, Android, and iOS. 

GET /orders HTTP/1.1
Host: api.manitou.example
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
Accept: application/json

"Bearer" means precisely what it says: whoever bears this token is treated as the user. There's no second factor, no device binding, no challenge. The token is the credential.

Two consequences follow directly, and they drive most of the rest of this document:

Transport must be HTTPS A bearer token sent over plain HTTP is readable by anyone on the network path, and replayable by them. Section 8 of PROJECT_PLAN.md requires HTTPS everywhere for exactly this reason.
Storage matters enormously A stolen token is a stolen session. Where the client keeps it is a security decision, not a convenience one — see section 10.
Naming detail

The header is Authorization, even though it carries authentication. A historical misnomer, baked into HTTP since the 1990s and never going to change. Don't let it confuse the AuthN/AuthZ distinction from section 01.

05

The decision

Both options below produce the same JWT and use the same Bearer scheme afterwards. The only question is how the login request itself is packaged.

Option 1 — JSON bodyRecommended 
POST /auth/login
Content-Type: application/json

{ "email": "admin@manitou.local", "password": "admin" }

→ { "access_token": "eyJ...", "token_type": "bearer" }

Ordinary JSON in, ordinary JSON out — identical in shape to every other endpoint in the API.

Consistent Same content type as register, products, cart, checkout. No exception for any client to remember.
No dependency Needs nothing beyond what's already in requirements.txt.
Natural field names The field is called email, because it is one.
Manual in /docs Call login, copy the access_token, paste into Swagger's Authorize box. Once per session.
Option 2 — OAuth2 password formFastAPI standard 
POST /auth/login
Content-Type: application/x-www-form-urlencoded

username=admin@manitou.local&password=admin

FastAPI's built-in OAuth2PasswordRequestForm, modelled on the OAuth2 spec's password grant.

Nicer /docs Swagger's Authorize button becomes a real login form and applies the token automatically.
Inconsistent Form-encoded, while the rest of the API is JSON. Web, Android, and iOS each need a special case for this one call.
Extra dependency Requires python-multipart to parse form data.
Misleading field The field must be named username even though it holds an email.
Solves a bigger problem OAuth2 exists for delegated third-party authorization — grant types, scopes, external identity providers. Manitou has none of that.
Why Option 1 for Manitou

The /docs inconvenience costs a few seconds, once per session, only during development. The client inconsistency is permanent and spans three separate codebases. Section 2 of PROJECT_PLAN.md makes one uniform API contract the architectural centrepiece — an exception at the front door undercuts it.

Reaching for the OAuth2 machinery here is also precisely the "generalize ahead of need" pattern CLAUDE.md rules out. If Manitou ever adds "Sign in with Google," that's a real OAuth2 flow — and it would be built then, deliberately, not approximated now.

06

Password hashing

What happens on the server side of that first login — and the one part of authentication where getting it wrong is unrecoverable.

Hashing is not encryption

Encryption is reversible by design: with the key, you recover the original. Hashing is deliberately one-way — there is no operation that turns a hash back into the password. Verification works by hashing the submitted password again and comparing the results.

This means that if your database is stolen, the attacker gets no passwords — only hashes that must be brute-forced one at a time. That property is the entire point.

Why bcrypt, not SHA-256

SHA-256 is a hash, but the wrong kind here: it's built to be fast, which is exactly wrong for passwords. Fast hashing means an attacker with a stolen database can test billions of guesses per second. bcrypt is deliberately slow, and tunably so. 

$2b$12$LQv3c1yqBWVHxkd0LHAkCOYz6TtxMQJqhN8/LewKyF3XGvA1Kk8Vy
└┬┘└┬┘ └──────────────────┬─────────────────────────────────┘
 │  │                     │
 │  │                     └── 22-char salt + 31-char hash
 │  └── cost factor: 2¹² = 4,096 rounds
 └── algorithm variant (bcrypt 2b)
Salt A random value generated per password and stored inside the hash string. Two users with the identical password get completely different hashes — which defeats precomputed rainbow tables and stops an attacker learning that two accounts share a password.
Cost factor Each increment doubles the work. Cost 12 is a reasonable current default. You raise it over the years as hardware improves — the tunability is why bcrypt has aged well.
Fixed 60 chars Every bcrypt hash is exactly 60 characters, whatever the password's length. Useful as a sanity check.
You have already seen this

Challenge C5 in the SQL exercises inspects exactly this: LEFT(password_hash, 7) returns $2b$12$ and LENGTH() returns 60 — the algorithm variant, the cost factor, and the fixed width, read straight off your seeded admin row.

Timing

Always use the library's own comparison function (bcrypt.checkpw), never == on hash strings. Proper implementations compare in constant time, so an attacker can't learn how much of a guess was correct by measuring how long the rejection took.

07

Registration

Creating the account that login later authenticates. Shorter than login, with one security decision that matters more than all the rest combined. 

  Client                                      API                        Database
    │                                          │                             │
    │  POST /auth/register                     │                             │
    │  { email, password, full_name }          │                             │
    ├─────────────────────────────────────────▶│                             │
    │                          1. validate shape (Pydantic)                  │
    │                          2. hash password (bcrypt)                     │
    │                          3. force role = "customer"                    │
    │                                          │  INSERT INTO users ...      │
    │                                          ├────────────────────────────▶│
    │                                          │                             │
    │                                          │◀────────────────────────────┤
    │                                          │  unique violation on email? │
    │                          4. map DB error → 409 Conflict                │
    │  201 Created                             │                             │
    │  { id, email, full_name, role }          │                             │
    │◀─────────────────────────────────────────┤                             │

The one rule that matters most

Never accept role from the request body

If the registration endpoint reads role from client input, anyone can POST {"email": "...", "password": "...", "role": "admin"} and grant themselves the vendor portal. This is not a hypothetical — it is one of the most common real-world API vulnerabilities, usually introduced by passing the whole request body straight into the model constructor.

The role is assigned by the server, always. Public registration hardcodes role="customer". The Pydantic schema for the request must not contain a role field at all — that way the value cannot arrive even if someone sends it.

In Manitou there is exactly one admin, created by seed.py. There is no public path to becoming one, which is the correct shape for a single-vendor store — the scope boundary in Section 1 of PROJECT_PLAN.md doing quiet security work.

Validation belongs in the schema

Pydantic enforces the request shape before your endpoint code runs, so invalid input never reaches the database. A registration schema typically constrains:

Email format Pydantic's EmailStr validates the shape. Normalise to lowercase before storing — otherwise Jose@x.com and jose@x.com become two accounts, since the unique constraint is case-sensitive.
Password length A minimum (8–12 characters is a reasonable floor). Length matters far more than forced symbol/number rules, which mostly push people toward predictable substitutions.
Maximum length Cap it (say 128). bcrypt silently truncates input beyond 72 bytes — an unexpected behaviour worth guarding against explicitly rather than discovering later.
No role field Its absence from the schema is the enforcement mechanism.

Duplicate emails, and an honest tension

The users.email unique constraint from Section 6.5 means a duplicate registration raises a database integrity error. Catch it and return 409 Conflict rather than letting a 500 escape.

A genuine conflict with §13

The anti-patterns section says never reveal whether an email exists — yet registration inherently must: "this email is already taken" is that disclosure. There's no clean way around it, because the user genuinely needs to know why their signup failed.

The standard resolution is asymmetric handling. Login stays deliberately vague ("invalid email or password"). Registration is allowed to be specific, because the alternative is an unusable signup form. High-security products avoid it by always returning success and sending an email that says either "confirm your account" or "you already have one" — a real technique, and more machinery than Manitou needs.

Two smaller decisions

Auto-login after register? Returning a JWT straight from /auth/register saves the user an immediate second step. Returning only the created user, and requiring a separate /auth/login call, keeps each endpoint doing one thing and keeps token issuing in one place. Either is defensible — pick one and be consistent, since the mobile apps in Phase 7 will assume whatever the web client does.
What to return Never include password_hash in a response. Use a separate Pydantic response model that simply omits it — relying on remembering to strip it manually is how it eventually leaks.
08

Enforcing the role

The AuthZ half of task 1, and the mechanism the entire Phase 4 vendor portal rests on. In FastAPI this is dependency injection, which makes the check reusable rather than repeated.

The chain

  Request with Authorization: Bearer eyJ...
       │
       ▼
  get_token          extract the header, strip the "Bearer " prefix
       │                  missing/malformed ──▶ 401
       ▼
  get_current_user   verify signature, check exp, read "sub" claim
       │                  invalid/expired ──▶ 401
       │                  load the user row from the database
       ▼
  require_admin      compare role against what the route demands
       │                  authenticated but wrong role ──▶ 403
       ▼
  endpoint runs

Each layer depends on the one above it, so a route declares only the level it needs — and the checks below come along automatically. 

# app/deps.py — the shape, not the finished code

async def get_current_user(token: str = Depends(oauth2_scheme)) -> User:
    """401 if the token is missing, malformed, expired, or forged."""
    payload = jwt.decode(token, settings.jwt_secret, algorithms=["HS256"])
    user = session.get(User, int(payload["sub"]))
    if user is None:
        raise HTTPException(401, "Could not validate credentials")
    return user


async def require_admin(user: User = Depends(get_current_user)) -> User:
    """403 if authenticated but not an admin."""
    if user.role != "admin":
        raise HTTPException(403, "Admin access required")
    return user

Routes then declare their requirement rather than implementing it: 

@router.get("/orders")                       # any logged-in user
async def my_orders(user: User = Depends(get_current_user)):
    return orders_for(user.id)

@router.post("/admin/products")              # admin only
async def create_product(user: User = Depends(require_admin)):
    ...

401 vs 403 — a distinction worth getting right

Status Means Client should
401 Unauthorized Not authenticated. No token, malformed token, bad signature, or expired. Redirect to login, or refresh the token and retry.
403 Forbidden Authenticated fine, but this role isn't permitted here. Show a "not allowed" message. Logging in again won't help.

Note the naming is backwards from the concepts in §01: 401 is about authentication despite being called "Unauthorized," and 403 is about authorization. Another historical HTTP misnomer, like the Authorization header itself. Getting these right matters practically — the Phase 3 web client needs to distinguish "your session expired, log in again" from "you're not an admin," and it does so purely from the status code.

Read the role from the token, never from the request

get_current_user takes the user id from the verified JWT payload, then loads the role from the database. A route that trusted ?role=admin, a request body field, or a custom header would be trivially bypassable.

A design choice worth making deliberately: the role can come from the token claim directly, or be re-read from the database on each request. The claim is faster (no query); the database is fresher. If an admin is demoted, a role baked into their token stays admin until it expires — the same revocation problem from §09, in a different costume. Re-reading from the database avoids it, at the cost of one lookup per request. For Manitou's scale, the database read is cheap and the correctness is worth it.

Why this belongs in one place

Writing the token check inline in each endpoint means every new route is a chance to forget it — and a forgotten check is an open door with no error to notice. A dependency makes the secure path the default and the omission visible: a route with no Depends is obviously public, at a glance.

This is also what §13's "checking the role only in the UI" warns against. Phase 4 hides the admin link from customers, but that's presentation. require_admin is the actual control, and it holds even when someone calls the API directly with curl.

09

Token lifetime

The unavoidable tension: short-lived tokens are safer, and long-lived tokens are pleasanter. The standard resolution is to use two tokens with different jobs.

The tension

A JWT's central feature — the server verifies it without a database lookup — creates its central problem: a JWT cannot be un-issued. Once signed, it is valid until exp passes, regardless of what happens afterwards. Change your password, delete your account, get your laptop stolen: any already-issued token keeps working until it expires. That's why exp is not optional, and why it should be short.

Access token + refresh token

Access token Refresh token
Lifetime Minutes (15–60 typical) Days to weeks
Sent On every request Only to /auth/refresh
Purpose Prove identity to the API Obtain a new access token
Stored server-side? No Yes — so it can be revoked
Exposure High — travels constantly Low — travels rarely

The refresh token is deliberately stored in the database, which restores the revocation ability JWTs lack. Logging out, or a password change, deletes the refresh token row — so the session dies within one access-token lifetime rather than lasting weeks.

Refresh token rotation is the standard hardening: each refresh issues a new refresh token and invalidates the old one. If a rotated token is ever replayed, that's proof of theft, and the whole token family can be revoked.

Scope note for Phase 2

Task 1 asks for access tokens only — refresh tokens are not in the Phase 2 checklist. That's a reasonable starting point: a single access token with a sensible exp is a complete, working auth system. Refresh tokens are a natural Phase 8 hardening item, and the place to add them is when session expiry genuinely becomes annoying — not before.

10

Where the client keeps it

The token is a bearer credential, so this is the highest-stakes client-side decision in the whole system. There is no option with no downside.

Web (Phase 3)

Option Vulnerable to Verdict
localStorage XSS. Any injected JavaScript — from your code or any dependency — can read it and exfiltrate it. Common, convenient, and the weakest choice.
sessionStorage XSS, identically. Only benefit is that it clears when the tab closes. Marginally better than localStorage. Same core flaw.
In-memory (JS variable) Nothing persistent — but lost on every refresh, so it needs a refresh token to be usable. Good, paired with a refresh token in a cookie.
httpOnly cookie CSRF — but that is well-mitigated by SameSite=Strict or Lax. Unreadable by JavaScript, so XSS cannot steal it. Strongest default for a browser client.
The tradeoff, stated plainly

You are choosing which attack to defend against. XSS means an attacker runs JavaScript in your page; CSRF means a malicious site triggers requests using cookies the browser sends automatically.

CSRF has a complete, standard, one-flag mitigation (SameSite). XSS has no equivalent single fix — if arbitrary JavaScript runs in your page, anything JavaScript can read is gone. That asymmetry is why httpOnly cookies generally win: you trade an unsolved problem for a solved one.

Mobile (Phase 7)

Native apps have no browser storage and no XSS surface, but they do have device theft and rooted devices. Both platforms provide OS-level encrypted stores backed by hardware:

iOS (Swift) Keychain Services — encrypted, hardware-backed, survives reinstall if configured. Never UserDefaults, which is plain text.
Android (Kotlin) EncryptedSharedPreferences backed by the Android Keystore. Never plain SharedPreferences.

The mistake to avoid on both platforms is the easy one: writing the token to whatever simple key-value store the SDK offers by default, which is unencrypted and readable on a compromised device.

11

Attack surface

What actually goes wrong, and what stops it.

Attack How it works Defence
Credential stuffing Attacker replays email/password pairs leaked from other breaches against your login endpoint. Rate limiting on /auth/login (Phase 8), account lockout, and eventually MFA.
Brute force Automated guessing against one account. Rate limiting plus bcrypt's deliberate slowness, which caps attempts per second.
Token theft (XSS) Injected JavaScript reads the token from browser storage and sends it elsewhere. httpOnly cookies, a Content Security Policy, and escaping all user-rendered content.
Token replay Token captured in transit and reused by the attacker. HTTPS everywhere, plus short exp to bound the damage window.
CSRF A malicious page triggers authenticated requests using cookies the browser attaches automatically. SameSite=Strict or Lax; CSRF tokens for anything sensitive.
alg: none Attacker resubmits a token with the algorithm set to "none," hoping the server skips verification. Pin the expected algorithm explicitly when decoding. Any current library defaults to safe behaviour — never disable it.
User enumeration Login errors that distinguish "no such email" from "wrong password" let an attacker map valid accounts. Return one identical generic error for both cases.
Secret leakage JWT_SECRET committed to Git; anyone holding it can forge any token, including admin ones. Section 4.2 of PROJECT_PLAN.md — .env locally, Secrets Manager in production, never in Git.
12

JWT vs server sessions

The alternative approach, and an honest account of what Manitou gives up by not using it.

With server-side sessions, the server stores session state (in memory, Redis, or a table) and hands the client only an opaque random ID. Every request looks that ID up.

JWT (Manitou's choice) Server sessions
Verification No lookup — signature check only Store lookup per request
Revocation Hard — valid until exp Instant — delete the row
Horizontal scaling Trivial — any instance can verify Needs shared session storage
Mobile clients Natural fit — just a header Workable but cookie-oriented
Payload visibility Claims readable by the holder Opaque ID reveals nothing
Size on the wire Hundreds of bytes, every request A short ID
Honest assessment for Manitou

JWTs are the right call here mainly because of the mobile apps: one identical auth mechanism serves the web, Android, and iOS clients, which is the same reasoning behind the one-API architecture in Section 2.

But the revocation weakness is real, not theoretical. "Log out everywhere" and "lock a compromised account immediately" are genuinely harder with JWTs, and the honest fix is a refresh-token table — which quietly reintroduces some of the server-side state JWTs were supposed to avoid. That is the standard, accepted compromise, not a flaw unique to this design.

13

Anti-patterns

Concrete mistakes, roughly in order of how damaging they are.

Storing passwords reversibly

Plain text, encrypted, or hashed with a fast algorithm like MD5 or SHA-256. Unrecoverable once breached, and it exposes every user who reused that password elsewhere. Use bcrypt (or argon2/scrypt).

Putting secrets in the payload

Base64 is not encryption. Anything in the claims is readable by whoever holds the token.

Omitting exp

A token with no expiry is a permanent credential you cannot withdraw.

Committing JWT_SECRET

Anyone with the secret forges admin tokens at will. And if it is ever committed, rotating it is the only fix — deleting it in a later commit leaves it in Git history.

Trusting client-supplied roles

The role must come from the verified token, never from a request body or query parameter. A client that can say ?role=admin is not an access control system.

Distinguishing login failure reasons

"Email not found" versus "incorrect password" hands an attacker a list of valid accounts. One generic message for both.

Logging tokens or passwords

They end up in CloudWatch in plain text, readable by anyone with log access, retained indefinitely.

Checking the role only in the UI

Hiding the admin link is presentation, not security. Every protected endpoint enforces its own role check server-side, because clients can call the API directly.
