Manitou Reference · Catalogue · Architecture

Grouping
the Catalogue

Sets, series, archives, catalogues, collections. Five words that sound like five names for one feature and are not. They describe three different mechanisms, one of which should never be a table at all. This document sorts them, gives a procedure for deciding which you actually have, and says what each one costs in the schema — including the one Manitou is about to take a shortcut on, and what unwinding it would cost.

00

Three mechanisms

Don't sort these words by what they're called. Sort them by what kind of statement membership is. That one question predicts the storage, the admin screen, and the way the feature rots.

A fact

membership is intrinsic

“This is a t-shirt.” True regardless of who is asking or what month it is. A product has exactly one answer, and the answers nest — a t-shirt is apparel.

products.category_id

An opinion

membership is curated

“These six go together as Spring 2026.” Someone decided it, someone can revise it, groups overlap, order inside them matters, and the group itself has a name and a story to tell.

collections + product_collections

A consequence

membership is derived

“We don't print this any more.” Nobody should be typing this in — it follows from stock, from dates, from is_active. It is a question, not a place.

a WHERE clause · no table

The third one is where catalogues go wrong. “Archive” sounds like somewhere you put things, so it gets built as a table with a flag someone has to set. It works for a month. Then a product sells out and nobody remembers to file it, and now the archive is a page that confidently lists the wrong products. A derived group cannot drift out of date because there is nothing to forget.

The same three mechanisms as schema. Note what the third panel does not contain.

01

The five questions

Answer these before naming the thing. The name is the part that misleads — “collection” and “category” sound interchangeable and are not, while “series” can be either depending on the catalogue.

QuestionIf noIf yes
Q1 Can one product be in two of these at once? A single reference will do — the category tree already is one You need many-to-many. Nothing else is honest
Q2 Does one of them contain another? Flat list A tree — parent_id and a recursive walk
Q3 Could a correct answer be computed from data you already store? It has to be recorded Stop. Do not store it. Write the query
Q4 Does the group need its own name, blurb, image or dates? It's a label — a tag It's an entity — its own table
Q5 Does the order of products inside it matter? Sort by whatever the list page sorts by position on the membership, not on the product

Q3 short-circuits the rest. If the answer is yes, none of the other four matter — you have a query, and building a table for it is how you get a page that lies. Ask it early.

Q5 is the one people get wrong quietly. Order belongs on the membership, because a product's place is per-group: first in “New in”, seventh in “Gifts”. A sort_order column on products can only ever express one of those, and it will be the wrong one on every page but the first that used it.
02

The words, decided

Each of the five run through the procedure. Two of them are traps — words that name something other than a grouping, where building the obvious thing means building the wrong thing.

WordUsually meansQ1 many?Mechanism
Category What kind of thing this is no Single FK, nested. Built.
Series What we released together, numbered usually — but see below Join table, or the category tree if genuinely one-per-product
Collection What we grouped for a reason yes Join table. No shortcut survives here
Set Ambiguous — ask which — Either a collection, or not a grouping at all
Archive What we no longer sell — A query. Not a table
Catalogue All of it — or a published document — Not a grouping. Find out which meaning

The trap in “set”

“Set” carries two meanings and they cost wildly different amounts. One is a curated group — a collection by another name, a few days' work. The other is a sellable bundle: “gift set of three”, one thing a customer adds to the cart that is made of other products.

That second one is not a grouping feature. It reaches into inventory (buying the set has to decrement three components, and go out of stock when any one of them does), into pricing (the set is usually cheaper than its parts, so which price is authoritative?), into order_items (does the snapshot record the set or the components?), and into fulfilment (one parcel, three things to pick). It is weeks, not days. Ask which one is meant before writing anything.

The trap in “catalogue”

Most of the time it means “everything we sell”, which is the product list you already have. Occasionally it means a published artefact — a PDF, a printed lookbook, “the 2026 catalogue” — which is a document with a date and a download, not a data structure. If someone asks for the catalogue, find out whether they want a page or a file.

Why “archive” resists being a table

Three plausible meanings, and all three are already computable:

  • “Sold out and not returning” — no variant has sellable stock and nothing is on order.
  • “A series we finished” — the collection has an ends_at in the past.
  • “Hidden from the shop” — that is is_active = false, which exists.

Each is a WHERE clause over rows Manitou already keeps. Add an is_archived flag beside them and you have created a fourth answer that can disagree with the other three — and it will, because it is the only one a human has to maintain.

The one case that justifies storing it: when the archive is an editorial act rather than a status — “these twelve are the ones we are proud of.” That is an opinion, so it is a collection, and it goes through the ordinary mechanism with a name like Archive. The rule holds: opinions get stored, consequences get queried.
03

Categories as series

Phase 7 task 6 says “the categories are the series” — Field Guide, Emblem, Poster, Orbit OS as four top-level categories rather than a product-type tree. That is a decision with preconditions, and it is worth writing them down while it is still reversible.

The stated reason was sound: products.category_id is NOT NULL and single, and the Orbit OS capsule spans a tee, a tote and a cap — so a T-Shirts / Accessories tree would have split one design across two branches with no way to reunite it. Given one axis, release is the more useful axis for this catalogue.

What has to stay true

PreconditionTrue today?The day it breaks
Every product belongs to exactly one series yes “Put this shirt in Field Guide and Gifts Under $35.” You can't. Duplicating the product duplicates its SKUs and splits its stock
Nobody needs to browse by product type yes “Show me all the t-shirts.” There is no such page, because the tree is organised by release
Series don't accumulate faster than the nav can hold yes — four Every past series is a permanent nav row. CategoryNav renders them all, flat and alphabetical
A product never leaves a series while staying on sale yes Retiring a series means reassigning or hiding every product in it first — category_id is NO ACTION

What unwinding costs

Adding collections later is cheap: two tables, additive, no backfill. The expensive part is not the schema — it is the data. If the category tree has been carrying release information, then on the day real collections arrive somebody has to decide what a category means again, and re-file every product. That is a data migration with judgement in it, and judgement does not batch.

Its cost is proportional to catalogue size. Today production holds two products, and the Field Guide categories have not been created yet — so the decision is currently free to reverse. At two hundred products it is an afternoon of someone's careful attention. That asymmetry is the whole reason this section exists.

Keep it, and write down the trigger

At this size the shortcut is correct, and the alternative — building a collections system for a planned catalogue of eleven products across four groups — is exactly the speculative generalisation Section 1.1 forbids.

Revisit the first time any of these happens: a product needs to be in two groups at once; somebody asks for a page listing one product type; or the header passes roughly six categories. Any one of them means the single axis has run out, and that is the moment to spend the migration — not before, and not several series later.

04

The schema

Four ways to add a second grouping axis, in ascending order of what they cost and what they buy.

OptionCostCeiling
A · Nothing
today		 None One axis. One group per product
B · A second nullable FK
products.collection_id		 One migration, no backfill Two axes, still one membership each. You will want a third, and then you are here again
C · Join table
collections + product_collections		 One migration, two tables, endpoints, an admin screen, a route The general answer. Many groups, ordered, each with its own content
D · JSONB array on products Looks like the cheapest Don't. No foreign keys, so a deleted collection leaves dangling names; nowhere to put position; nowhere for the group's own blurb and image; and “what is in this collection” needs a GIN index to stop being a scan

The shape of C, when it is time

collections
  id            bigint  PK
  name          text    not null
  slug          text    unique          -- /collections/{slug}
  description   text    null
  hero_image    text    null            -- same URL rules as product_images
  starts_at     timestamptz null
  ends_at       timestamptz null        -- past ends_at IS the archive
  is_active     boolean not null default true
  created_at    timestamptz not null default now()

product_collections
  product_id    bigint  FK -> products.id
  collection_id bigint  FK -> collections.id
  position      int     not null default 0
  PRIMARY KEY (product_id, collection_id)
  • No parent_id. Collections do not nest. A nested collection is two axes wearing one coat — and you already have a tree for the axis that genuinely nests.
  • The composite primary key is what stops the same product being added to the same collection twice, which is otherwise the first bug an admin screen produces.
  • Index collection_id separately. The PK serves “which collections is this product in”; the reverse — “what is in this collection”, the one every page asks — needs its own.
  • products.category_id does not change. It stays NOT NULL and keeps meaning “what kind of thing this is”. The whole point of adding an axis is that the first one gets to go back to being honest.
The migration is additive and needs no backfill, which is the same property that made product_images.applies_to safe to add in Phase 4.6: an empty product_collections means every product is in no collection, and that is precisely how the store behaves today. Nothing changes appearance when it is applied, and the downgrade loses configuration rather than content.
Write the CHECK constraints by hand. PROJECT_PLAN Section 6.8: Alembic autogenerate does not diff CHECK constraints on a table that already exists, and will silently produce an empty migration. A starts_at < ends_at guard needs op.create_check_constraint() with a matching op.drop_constraint(..., type_='check') in downgrade(), verified against pg_constraint.

What the API would gain, and what it would not

GET /collections and GET /collections/{slug}, mirroring the category pair. GET /products gains a collection filter beside category.

It would not need a recursive walk — services/categories.py::descendant_ids exists because categories nest and collections do not. Nor would it need a featured flag: store-config.json's home.featured.category already points the home page at a slug, and pointing it at a collection slug instead is a config change.

05

The grouping spec

Fill this in before building any new way to group products. It is one screen, it takes ten minutes, and it is much cheaper than the migration it prevents. Copy it into the pull request or the plan entry.

Working name
What people are calling it. Not necessarily what it is.
Membership is
Fact · opinion · consequence. If consequence, stop here and write the query instead.
Q1 · cardinality
Can a product be in two at once? Yes forces many-to-many.
Q2 · nesting
Does one contain another? Be suspicious — usually this is two axes.
Q4 · the group's own fields
Name only means a tag. Name plus blurb, image or dates means an entity.
Q5 · ordering
Does position inside the group matter? If so it lives on the membership.
Lifecycle
Does a group end? What happens to its products when it does — do they leave the shop, or just this page?
URL
What does it look like, and what happens to the old URL when a group is renamed?
Nav cost
How many rows does this add to the header, and how many after a year of them?
Who maintains it
Which human, doing what, how often.
What it looks like neglected
The most important line here. Describe the page after six months of nobody touching it. If the answer is "wrong", the design is wrong.
The last row does most of the work. A category tree neglected for a year is still correct — a t-shirt is still a t-shirt. A hand-maintained “New in” neglected for a year is a page of year-old products presented as new, which is worse than not having the page. Prefer groupings that degrade into being merely stale over ones that degrade into being untrue.
06

Clones

Should collections become a fifth reusability seam, pre-built so a clone inherits it? Section 1.1 sets the test: “They cost almost nothing in the default T-shirt build.”

Existing seamWhat it costs unused
unit_of_measureOne text column with a default
attributes JSONBOne column, {}
Store configA file that has to exist anyway
fulfilment.method + event sourceOne config key, one column on rows that are written regardless
A collections systemTwo tables, two endpoints, an admin screen, a storefront route, a nav decision — dead weight in every store that never groups anything

Not a seam — but one discipline

It fails the test plainly, and adding it would be the speculative generalisation the section exists to prevent. A clone that needs collections adds them in a day, from the shape in §04, against a schema that welcomes the addition.

What genuinely does cost nothing, and saves the expensive part: keep category meaning “what kind of thing this is.” The future migration is cheap; un-picking a category tree that was used as a release axis is not. Discipline now, not schema now.

And Manitou is about to break that discipline on purpose. Phase 7 task 6 files products by release, for the good reason in §03 — one axis, and a capsule that spans product types. That is the right call at eleven products. It is recorded here rather than left implicit so that a clone reading the seeded catalogue does not copy the shape without the reasoning, and so that whoever hits one of §03's triggers finds the cost already written down instead of discovering it.

For a clone that knows it needs both axes on day one — a broad catalogue, a grocery store with weekly specials — build §04's two tables before entering any products. The tables are cheap at any time; the re-filing is what gets expensive, and entering a catalogue under the wrong shape is how you buy it.
