00

What changed

Before Phase 5, an order was a row someone typed a status into. After it, an order is a claim on money and on goods, and both have to be true at the same time.

That single change is what made the phase larger than it looks. Adding Stripe is a day's work. What took the rest was every assumption that quietly depended on “placing an order” and “being paid” happening in the same instant — because they no longer do.

BeforeAfterWhat broke
An admin set an order to paid Stripe says so, via a webhook Nothing may trust the browser about money
Stock left the shelf at checkout Stock leaves when payment confirms Abandoned checkouts consumed stock forever
The cart emptied at checkout The cart empties when paid Abandoning lost the customer's basket
“In stock” meant one number Physical, reserved and sellable are three Five places asked the wrong one
The recurring shape. Most of the twenty defects were not new mistakes. They were code that had been correct and stopped being correct because the world around it changed. Worth remembering whenever a step a human used to perform becomes automatic: the question is not “is this still right?” but “what was this relying on that is no longer true?”
01

Money is an integer

Stripe does not accept 19.99. It accepts 1999.

Payment APIs take a whole number of the currency's smallest unit — cents, pence, öre. There is no decimal point anywhere in the request. This is not Stripe being awkward; it is the industry avoiding the most expensive bug class in financial software. 

>>> 19.99 * 100
1998.9999999999998
>>> int(19.99 * 100)
1998

A penny short on every order, forever, and nobody notices until reconciliation. It is the same reason every money column in the schema is numeric(10,2) and never a float.

Not every currency has cents

This is the half that catches people. Multiplying by 100 is not “the conversion” — it is the conversion for currencies that happen to have two decimal places. The yen has none. ¥500 is five hundred yen. Send 50000 and you have charged your customer one hundred times the price. 

CURRENCY_EXPONENT = {
    "USD": 2, "EUR": 2, "GBP": 2, "CAD": 2, "AUD": 2,
    "JPY": 0, "KRW": 0,
}
A missing entry raises rather than defaulting to 2. .get(code, 2) would have been shorter and would have worked for every currency in the table. It would also have silently overcharged 100× the first time this store was cloned for a Japanese market. Failing loudly costs a support ticket; guessing costs a chargeback and a customer.

The test that proved nothing

The first version of the test used 19.99 × 3 = 59.97, assuming an awkward price stays awkward once multiplied. It does not:

Totalfloat × 100int()Correct?
59.975997.05997a float version passes
32.303229.99999999999953229a cent short

16.15 × 2 = 32.30 distinguishes them. And note how ordinary 32.30 looks — there is no surface cue about which totals are dangerous, which is the entire argument for never letting money touch a float.

Curiosity worth keeping. Of 16.15 × 1…20, only ×1, ×2, ×4, ×8 and ×16 undercharge — the powers of two. Doubling is exact in binary, so it preserves the original representation error, while ×3 renormalises and washes it out.
02

Opening a payment

A PaymentIntent is an intention to collect money. Creating one charges nothing.

Why a seam, not a direct call

The app never says “call Stripe”. It says “create a payment intent”, and a Protocol decides who hears that — the real gateway, or an in-memory fake. Without it, every test that places an order would need a network round trip and a live secret key: the suite would stop being runnable offline and would leave money-shaped debris in a real account.

A fake that does not imitate what you depend on is a fake that lies. FakePaymentGateway replays on a repeated idempotency key, exactly as Stripe does. A lazier fake would mint a new intent every call — and a test asserting “asking twice reuses one payment” would then pass for the wrong reason.

Idempotency is keyed to the order

idempotency_key = f"order-{order.id}"

Stripe remembers the key and replays its original response rather than opening a second payment. A double-clicked “Place order”, or our own retry after a timeout that actually succeeded, cannot produce two charges. Keyed to the request instead — a fresh UUID per HTTP call — it would have looked like idempotency and protected against nothing.

Never hold a lock across a network call

Checkout takes SELECT … FOR UPDATE row locks on inventory, and holds them until commit. Opening the Stripe intent inside that window would mean every concurrent buyer of the same item queues behind a third party's latency — and a slow Stripe becomes a database stall, with connections piling up on locks.

wrong right ┌ BEGIN ┌ BEGIN │ lock inventory rows │ lock inventory rows │ create order │ create order │ ── call Stripe ── ⏳ 200ms └ COMMIT locks released └ COMMIT ── call Stripe ── ⏳ 200ms locks held for the round trip nobody is waiting on us

The cost of that choice: the order and the payment are no longer one atomic unit. There is a real window where the order exists and the payment does not — which is why the failure message has to carry two facts at once.

“Your order was saved, but we could not start the payment. Nothing has been charged.” Both halves earn their place. Without the first, the customer rebuilds their cart and orders twice. Without the second, they check their bank statement in a panic.
03

Collecting a card

The card number never enters our page. That is a structural property, not a promise.

BROWSER NEXT.js FastAPI STRIPE │ GET /orders/42/pay │ │ │ │────────────────────>│ POST payment-intent │ │ │─────────────────>│ create/retrieve │ │ │───────────────>│ │ HTML + clientSecret│<─────────────────│<───────────────│ │<────────────────────│ │ │ │ │ │ ┌── iframe from js.stripe.com ──┐ │ │ │ 4242 4242 4242 4242 │ card ──────────────>│ │ └───────────────────────────────┘ never in our DOM │ │ │ │ confirmPayment(clientSecret) ──────────────────────────>│

The input lives in an iframe served by js.stripe.com. Same-origin policy means our JavaScript cannot read across that boundary — not the value, not the keystrokes. A compromised npm dependency running in our bundle still cannot see a card number. The moment those digits are in our DOM they are in our logs, our error reports and our PCI scope.

Three keys, three different rules

KeyLivesCan
sk_test_… secret Server only, SecretStr Charge, refund, read every customer. Treat like the database password.
pk_test_… publishable NEXT_PUBLIC_, inlined into the browser bundle Only start a payment the secret key already authorised
client_secret Returned to one browser, never stored Confirm this one payment. Nothing else.
Why the client secret is safe to send and never written down. It authorises exactly one payment — whoever holds it can pay this order and cannot read a customer, refund anything, or touch another order. That narrowness is why it may reach a browser at all. It is not stored because anything written down can leak from a backup, a log or a stray SELECT *, and it can always be re-fetched from Stripe.

The secret key is wrapped in SecretStr so a traceback prints ********** rather than the key. That was adopted after a boot failure printed a live key into an error message — harmless on a laptop, and from Phase 6 the same crash writes it to CloudWatch.

04

Confirming payment

Only Stripe may say that money moved — and it says so to the server, not to the browser.

The browser is the one party in this exchange with a reason to lie about payment. So confirmation arrives by webhook: Stripe's servers POST to ours. That endpoint is public and unauthenticated — Stripe has no account here, no JWT, no cookie. Anyone on the internet can post to it.

What stops a stranger posting “paid”

A shared secret and an HMAC. Stripe signs each delivery and sends the signature in a header: 

Stripe-Signature: t=1724236800,v1=5257a869e7eceb…

v1 = HMAC-SHA256(whsec_…, f"{t}.{raw_body}")

Recomputing that proves the sender held the secret. The timestamp is inside the signed string, so a captured request cannot be replayed days later.

The single most common way this breaks: using the parsed body. Take FastAPI's parsed JSON, re-serialise it to compute the HMAC, and you get different bytes — different whitespace, different key order — so the signature never matches. The endpoint must read await request.body() and hand those exact bytes through.

At-least-once, not exactly-once

Stripe does not promise one delivery. It promises at least one, and retries for days until answered with a 2xx. The same payment_intent.succeeded will arrive more than once.

So the rule has to be idempotent by construction: applying it five times must leave what applying it once leaves, and must not write five audit rows. A trail claiming an event happened five times is worse than no trail — it describes something that did not occur.

Almost everything answers 200

SituationAnswerWhy
Valid, handled event200Applied
Event type we ignore200A 4xx has Stripe redelivering account.updated for three days
An intent we have no record of200Another integration, or a CLI test event. No retry will ever help.
Bad signature400The sender was not Stripe, so there is nobody to retry
The response body says nothing. Telling a forger which part of their signature failed is telling them what to fix. The real reason goes to the log instead.

Money for an order nobody will fulfil

A customer pays after the vendor cancelled. The order is not revived: cancelling released the stock and the customer may already have been told, so reinstating it would overrule a person and could commit the store to goods it no longer has. The payment is mirrored, a payment.conflict row names the clash, and a human decides.

The pull half: when the push is missed

Webhooks are missed — the endpoint is down during a deploy, or (as here) it did not exist yet. Stripe retries for about three days and then stops forever. A push-only integration has a failure mode with no recovery.

Hence a Re-check payment action in the vendor portal, which asks Stripe and applies the same rule. Not a second implementation — the same function — because two copies of a money rule eventually disagree, and you find out when one path marks an order paid and the other does not.

05

Stock is a promise

“There are five on the shelf” and “you can buy five” stopped being the same sentence.

Checkout used to do quantity_available -= qty at order creation. That was correct while pending → paid was a human decision — an order was as good as a sale. It became wrong the moment payment turned into a step that can simply never happen: an abandoned checkout consumed its stock permanently. Ten items and ten abandoned carts leaves a product reading sold out having earned nothing.

FigureMeansStored?
quantity_availablePhysically on the shelfYes
reservedHeld by pending ordersNo — derived
sellableavailable − reservedNo — derived

The pending order is the reservation

Its order_items rows are the hold. Placing an order writes nothing extra, releasing one is just the status changing, and a “missed release” is not a bug that can exist — there is no counter to drift because there is no counter.

A maintained counter

Cheap to read. Drifts if any release is ever missed, and a drifted reservation is invisible stock loss nobody can trace. Expiry needs a scheduled sweep.

Derived from pending orders

Cannot drift — the orders are the truth. Expiry is one WHERE clause, no scheduler. Costs an aggregate per read.

Expiry without a scheduler

AND o.created_at > now() - interval '30 minutes'

An abandoned order simply ages out of the query. No cron, no sweep job, no background worker — which suits a single container. The window lives in store-config.json, because a grocery clone picking stock the same morning wants a much shorter one than a T-shirt store.

The dangerous part: five call sites

Five places ask “is there stock?” — the oversell guard, the storefront, the cart, add-to-cart, and the vendor's inventory screen. Leaving one on quantity_available does not merely weaken the guard: it removes it, because that column no longer moves at placement.

Measured, not assumed. Reverting the checkout guard alone let 8 concurrent buyers sell the same 3 units. Each of the five sites now has its own test, verified by reverting each individually and confirming exactly one test fails.

Where the shelf actually moves

TransitionShelfWhy
→ paid−qtySold; they will be picked
pending → cancelledunchangedNothing ever left the shelf
paid → cancelled+qtyNever dispatched, so they are back
paid → refundedunchangedMay be shipped, damaged, or never returned
Cancelled and refunded look alike in a status column and are opposites in the warehouse. Both halves of the condition are load-bearing: drop “was paid” and cancelling a pending order manufactures stock out of an abandoned checkout; widen it to refunds and the store invents inventory that may never come back.

Deriving costs something — so it was measured

A benchmark database of 1,500 variants and 40,000 order lines, because the development database has 27 and Postgres will not use an index on a table that small. Measuring there would have produced a number that looked like evidence and was not.

QueryWith indexWithout
Product page (3 variants)1.0 ms8.5 ms
/admin/inventory (100 of 1,500)225 ms3,375 ms

Customer-facing paths are ~1 ms, because the catalogue listing never asks — it carries no variants. The 225 ms belongs to one internal screen, and the cause is not the subquery: ORDER BY a derived column forces computing it for all 1,500 rows before LIMIT applies (9 ms vs 142 ms). So the counter stays underived, and if it ever matters the fix is that sort — not a cache with drift to manage.

06

A cart is not a purchase

Reaching the payment step used to empty the cart — before any money moved.

The clerk scans your goods out of the trolley. But if you say “hold on, do not ring that up”, you do not walk away empty-handed. Ours did: abandon at the card form and the basket was gone.

Every major platform keeps the cart until payment succeeds. Abandonment runs around 70% industry-wide, and a cart that still holds its items is the entire basis of cart recovery. Emptying at the payment step throws that away and punishes a customer who merely wanted one more thing.

The same root as the stock defect, one layer up. Both treated “started to check out” as “bought”. The test guarding it has now been renamed twice for exactly that reason.

One pending order per customer

A surviving cart means someone can reach the payment step twice — and since reservations derive from pending orders, that would hold the same units under two orders. So checking out again supersedes the unpaid one. If the superseded order's payment lands anyway, from a card form left open in another tab, the conflict rule from §04 catches it.

Payment takes only what the order covered

Not “empty the cart”. Check out, abandon, add a jumper without checking out again, then pay the original order — emptying would silently bin the jumper. Subtracting the ordered quantities leaves it where the customer put it.

07

Decisions, and what was rejected

The reasoning matters more than the outcome; an outcome without its reason gets reversed by the next person who finds it inconvenient.

DecisionRejectedBecause
Only the webhook marks an order paid Trust the browser after confirmPayment The browser is the one party with a reason to lie about money
Currency exponent raises on a miss Default to 2 Guessing is a 100× overcharge for a zero-decimal currency
Reserved is derived A maintained counter A missed release is invisible, permanent stock loss
Paid-after-cancel is flagged Revive the order · auto-refund Never silently overrule a person; an automatic outbound refund is too much trust in one event handler
→ cancelled restocks, → refunded does not Treat them alike A refund may be shipped, damaged, or never returned
Cart shows the exact remaining count “Not enough stock”, no number A count for a line they already hold is a far narrower disclosure than the catalogue's
Card-only checkout Link · Klarna · bank Suppressing Link's in-card prompt removes the rows it brokers; BNPL earns little on a $25 basket
Pay button always enabled Disable until valid A dead button removes the feedback loop — the customer cannot ask why

How the defects were actually found

Twenty entries in docs/defect-log.md. Almost none came from a test failing — the suite was green throughout. They came from reading code and asking what it depended on, from using the store, and from mutation testing: breaking a guard on purpose to watch a test fail.

A guard you have never watched fail is not a guard. Twice in this phase a mutation was applied to the wrong line and “passed”, reading as this guard is untested when the guard had simply never been touched. The durable fix was to assert the match is unique before replacing it — a written lesson is not a habit.
