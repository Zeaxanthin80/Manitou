Querying JSONB

Reaching inside the attributes column — the Section 1.1 reusability seam, made concrete.

09All attributes, side by sideRaw view 
SELECT sku, variant_name, attributes FROM product_variants ORDER BY id;

Before filtering on anything, just look at the raw column. This is your actual answer to "what does the single-item product's attributes look like next to the others" — six populated objects, then one empty one, in the order seed.py inserted them.

Expected 
      sku      |  variant_name   |          attributes
---------------+-----------------+---------------------------------
 TEE-CLS-S-BLK | Small / Black   | {"size": "S", "color": "Black"}
 TEE-CLS-M-BLK | Medium / Black  | {"size": "M", "color": "Black"}
 TEE-CLS-S-WHT | Small / White   | {"size": "S", "color": "White"}
 TEE-CLS-M-WHT | Medium / White  | {"size": "M", "color": "White"}
 TEE-GRA-M-NVY | Medium / Navy   | {"size": "M", "color": "Navy"}
 TEE-GRA-L-NVY | Large / Navy    | {"size": "L", "color": "Navy"}
 BAG-TOTE-STD  | Canvas Tote Bag | {}
(7 rows)

The tote's {} isn't a NULL, a missing column, or an error — it's a genuinely valid, empty JSON object. That's the mechanism behind Section 1.1's reusability seam: the column always exists and is always valid JSONB, whether a store type needs zero attribute dimensions (this tote), two (these tees), or five (a grocery item with weight, brand, and organic status).

One incidental detail worth noticing: every object prints as size before color, even though nothing guarantees that ordering. JSONB doesn't preserve insertion order — internally it normalizes key order by length, then alphabetically. "size" (4 letters) sorts before "color" (5 letters) every time, regardless of how the Python dict in seed.py was written.

13The vanishing rowjsonb_object_keys()

The real gotcha the tote's empty {} creates. jsonb_object_keys() is a set-returning function — for each row, it produces one output row per key in the object. 06

Common Table Expressions

A CTE is a named temporary result set defined with WITH, available only to the query that follows it. Two distinct kinds: plain CTEs organise a query, and recursive CTEs walk trees of unknown depth.

Why these are here, given only 3 categories: a recursive CTE is genuine overkill for a two-level tree — a self-join (exercise 18) handles it. But the plan is to clone Manitou into a candle store and then a grocery store, and grocery catalogues nest deeply: Produce → Vegetables → Root Vegetables. These exercises build the pattern now, on data small enough to verify by eye, so it's familiar when depth arrives.

23A named intermediate stepWITH 
WITH product_stock AS (
    SELECT p.id, p.name, SUM(i.quantity_available) AS total_stock
    FROM products p
    JOIN product_variants v ON v.product_id = p.id
    JOIN inventory i ON i.variant_id = v.id
    GROUP BY p.id, p.name
)
SELECT name, total_stock
FROM product_stock
WHERE total_stock > 30
ORDER BY total_stock DESC, name;
WITH x AS (…)
defines a temporary named result, usable below like a table

Compare this to exercise 22 — identical result, different structure. There it needed HAVING SUM(...) > 30, because the filter ran on an aggregate mid-query. Here the aggregate is already computed and named, so the outer query uses a plain WHERE.

Expected 
        name        | total_stock
--------------------+-------------
 Canvas Tote Bag    |          40
 Classic Cotton Tee |          40
(2 rows)

That's the everyday value of a plain CTE: it splits "compute the totals" from "filter the totals" into two readable steps instead of one dense query. No new capability — just clarity, which matters once a query grows past a few lines.

24Two CTEs in one queryChained WITH 
WITH stock AS (
    SELECT v.product_id, SUM(i.quantity_available) AS units
    FROM product_variants v
    JOIN inventory i ON i.variant_id = v.id
    GROUP BY v.product_id
),
counts AS (
    SELECT product_id, COUNT(*) AS variant_count
    FROM product_variants
    GROUP BY product_id
)
SELECT p.name,
       c.variant_count,
       s.units,
       ROUND(s.units::numeric / c.variant_count, 2) AS avg_per_variant
FROM products p
JOIN stock s ON s.product_id = p.id
JOIN counts c ON c.product_id = p.id
ORDER BY avg_per_variant DESC;

Separate CTEs are comma-separated, and each can reference the ones before it. Computing two independent aggregates and combining them is awkward in a single query — this is where CTEs stop being cosmetic.

::numeric is a cast. Without it, units / variant_count is integer division and 25 ÷ 2 gives 12, not 12.5.

25Walking down a treeWITH RECURSIVE 
WITH RECURSIVE category_tree AS (
    -- anchor: where the walk starts
    SELECT id, name, parent_id, 0 AS depth
    FROM categories
    WHERE slug = 'apparel'

    UNION ALL

    -- recursive term: children of whatever we found last round
    SELECT c.id, c.name, c.parent_id, ct.depth + 1
    FROM categories c
    JOIN category_tree ct ON c.parent_id = ct.id
)
SELECT depth, name FROM category_tree ORDER BY depth, name;
Anchor
runs once — the starting row(s)
UNION ALL
joins the anchor to each recursive pass
Recursive term
references the CTE by its own name, re-running until it returns no rows

Read it as a loop: start at Apparel; find its children; find their children; stop when a pass finds nothing. The depth column is incremented each pass, so it records how far down each row was found.

Expected 
 depth |    name
-------+-------------
     0 | Apparel
     1 | Accessories
     1 | T-Shirts
(3 rows)

Why a self-join can't do this: each JOIN reaches exactly one level. Two levels needs two joins, five needs five — so you'd have to know the depth when writing the query. Recursion doesn't: it keeps going until nothing new turns up. That's the entire reason it exists, and why a grocery catalogue needs it while your T-shirt store doesn't.

26Walking up a treeBreadcrumbs 
WITH RECURSIVE breadcrumb AS (
    SELECT id, name, parent_id, 0 AS depth
    FROM categories
    WHERE slug = 't-shirts'

    UNION ALL

    SELECT c.id, c.name, c.parent_id, b.depth + 1
    FROM categories c
    JOIN breadcrumb b ON c.id = b.parent_id
)
SELECT name FROM breadcrumb ORDER BY depth DESC;

The same structure with the join reversed. Exercise 25 matched c.parent_id = ct.id (find my children); this matches c.id = b.parent_id (find my parent). One direction descends, the other climbs.

ORDER BY depth DESC puts the root first, which is the order a breadcrumb trail reads.

Expected 
   name
----------

(2 rows)

This is the Home / Apparel / T-Shirts trail at the top of a category page — real Phase 3 UI, not a theoretical exercise. At two levels it looks trivial; in a grocery store it's the only practical way to render the trail for an arbitrarily nested product.

27Products in a whole subtreeRecursive + JOIN 
WITH RECURSIVE subtree AS (
    SELECT id FROM categories WHERE slug = 'apparel'
    UNION ALL
    SELECT c.id FROM categories c
    JOIN subtree s ON c.parent_id = s.id
)
SELECT p.name, p.base_price
FROM products p
JOIN subtree s ON p.category_id = s.id
ORDER BY p.name;

The payoff query, and the one worth studying closest.

Expected 
        name        | base_price
--------------------+------------
 Canvas Tote Bag    |      18.00
 Classic Cotton Tee |      24.00
 Graphic Print Tee  |      29.00
(3 rows)

Look carefully at what just happened. Not one of those products has category_id pointing at Apparel — check exercise 01, every product sits in T-Shirts or Accessories. Yet asking for "everything under Apparel" returned all three.

That's the behaviour every real storefront needs: clicking a top-level category shows products filed three levels beneath it. Without recursion you'd get an empty page for Apparel, because nothing is filed there directly.

In a grocery store this is the difference between clicking Produce and seeing carrots filed under Produce → Vegetables → Root Vegetables, versus seeing nothing at all.

Two safety notes before you use recursion on real data. A cycle in the parent links — a category that is somehow its own ancestor — makes a recursive CTE loop forever. Your foreign keys don't prevent that, so a Phase 4 category editor must reject moves that would create one.

Second, UNION instead of UNION ALL deduplicates each pass, which is slower and rarely what you want here. Use UNION ALL unless you have a specific reason not to.

This is the actual query behind the Phase 4 reorder alerts — the threshold is per-variant data, not a hardcoded number. Note TEE-GRA-L-NVY (7 units) appears in C1 but not here: it's low, but still above its own reorder point.

C3Inventory valueArithmetic + COALESCE

Calculate the total retail value of all stock: price × quantity, summed across every variant. Remember price_override may be NULL, in which case the product's base_price applies. 

SELECT SUM(COALESCE(v.price_override, p.base_price) * i.quantity_available)
  AS total_retail_value
FROM inventory i
JOIN product_variants v ON v.id = i.variant_id
JOIN products p ON p.id = v.product_id;
 total_retail_value
--------------------
            2426.00
(1 row)

COALESCE(a, b) returns the first non-null argument — the standard way to express a fallback, and exactly the price-resolution rule from Section 6.3 written in SQL. The Large / Navy tee contributes 7 × 32.00 (its override), not 7 × 29.00.

LEFT() truncates so you don't paste a full credential into your terminal history — a good habit even for a local dev password. A bcrypt hash is always exactly 60 characters. The $2b$12$ prefix encodes the algorithm variant and the cost factor (12).

C6Category tree with countsRecursive + LEFT JOIN

Build the query a vendor portal's category sidebar needs: every category under Apparel, its depth, and how many products sit directly in it. Categories with none must still appear.

Two things to get right — which join type keeps the empty categories (remember exercise 16), and whether COUNT(*) or COUNT(column) gives the correct zero. 

WITH RECURSIVE tree AS (
    SELECT id, name, parent_id, 0 AS depth
    FROM categories WHERE slug = 'apparel'
    UNION ALL
    SELECT c.id, c.name, c.parent_id, t.depth + 1
    FROM categories c JOIN tree t ON c.parent_id = t.id
)
SELECT t.depth, t.name, COUNT(p.id) AS product_count
FROM tree t
LEFT JOIN products p ON p.category_id = t.id
GROUP BY t.id, t.depth, t.name
ORDER BY t.depth, t.name;
 depth |    name     | product_count
-------+-------------+---------------
     0 | Apparel     |             0
     1 | Accessories |             1
     1 | T-Shirts    |             2
(3 rows)

Both traps matter here. A plain JOIN would drop Apparel entirely, since nothing is filed directly in it — and COUNT(*) would count the LEFT JOIN's NULL row and report Apparel as having 1 product instead of 0. COUNT(p.id) counts only real matches.

Note this counts direct children only, which is what a sidebar usually shows. Counting the whole subtree — so Apparel reads 3 — means joining products against the recursive set as in exercise 27, rather than against each row individually. Worth trying as a follow-up.
