At a glance

Before the mechanics: what each one fundamentally is, in one line.

Password + JWT

You memorize a secret. The server checks it, then issues a signed token for subsequent requests.

Something you know

WebAuthn / FIDO2

Your device holds a private key it never reveals. It proves possession by signing a challenge.

Something you have

OAuth / OIDC

A third party (Google, Apple) vouches for you. You never give your password to the app you're logging into.

Delegated trust

SMS OTP

The server texts a short-lived code to your phone number; you type it back to prove you received it.

Something you have (weakly)
The framing to hold onto

These aren't four competitors for the same job. Password+JWT and WebAuthn both authenticate — they answer "who is this." OAuth/OIDC delegates that question to someone else. SMS OTP is usually a second factor bolted onto one of the others, not a standalone login method. Comparing them fairly means keeping straight which problem each one is actually solving.

01

The factor framework

Security literature groups authentication into a small number of "factors." Every method in this document is built from one or more of them.

Knowledge

Something only you should know.

Password, PIN, security question

Possession

Something only you should have.

Phone, hardware key, authenticator app

Inherence

Something you biologically are.

Fingerprint, face — usually unlocks a possession factor locally

Federated trust

Someone else already verified you.

"Sign in with Google" — not one of the classic three, but how OAuth/OIDC actually works

Multi-factor authentication means combining factors from different categories — a password (knowledge) plus an SMS code (weak possession) is genuine MFA. Two things you merely know — a password and a security question — is not, however different they feel; an attacker who learns one often learns both from the same breach.

Where each method sits

Password + JWT is pure knowledge. WebAuthn is possession, typically unlocked locally by inherence (Face ID, a fingerprint) — but that biometric never leaves your device; it's not sent anywhere. SMS OTP is possession, but of something increasingly easy to steal without stealing the physical phone (§05). OAuth/OIDC doesn't add a factor at all — it hands the whole question to a provider who already authenticated you some other way.

03

WebAuthn / FIDO2

The technology behind "passkeys." Structurally different from a password, not just a more convenient version of one.

The core idea: nothing secret ever crosses the network

Your device generates a key pair — a private key that never leaves it, and a public key it hands to the server. Logging in later means the server sends a random challenge; your device signs it with the private key; the server checks that signature against the public key it already has on file. The private key is never transmitted, never typed, and never visible to the server — not even once. There is no shared secret for a breach or a phishing page to capture.

Two ceremonies

REGISTRATION (once, when you enable it)

  Device                                    Server (relying party)
    │  "please register a credential"          │
    │◀─────────────────────────────────────────┤  sends a random challenge
    │  generate key pair, bound to THIS origin  │
    │  (manitou.example — not a lookalike)      │
    │  { public_key, credential_id }            │
    ├─────────────────────────────────────────▶│  stores the public key against your account

AUTHENTICATION (every login)

  Device                                    Server
    │◀─────────────────────────────────────────┤  sends a fresh random challenge
    │  unlock private key locally               │
    │  (Face ID / Touch ID / Windows Hello /     │
    │   device PIN — never sent anywhere)        │
    │  sign(challenge, private_key)              │
    │  { signature }                             │
    ├─────────────────────────────────────────▶│  verify against stored public key

Why this is structurally phishing-resistant, not just harder to phish

Origin binding

The key pair is cryptographically bound to the exact origin it was created for — manitou.example, specifically. A lookalike domain, manitou-example.com, physically cannot obtain a signature from a key that was never registered to it. This isn't user vigilance or a URL bar someone might not check — the browser itself enforces the match before the device will sign anything. A password has no equivalent: a person can be fooled into typing it anywhere. A private key cannot be fooled into signing for the wrong site.

Platform vs. roaming authenticators

Platform authenticatorBuilt into the device — Face ID, Touch ID, Windows Hello. The key lives in the device's secure hardware enclave.
Roaming authenticatorA separate physical security key (YubiKey and similar) connected via USB, NFC, or Bluetooth. Portable across devices.

Passkeys: the syncable evolution

Early FIDO2 credentials were bound to one physical device — lose the phone, lose the credential, full stop. Passkeys solve that by syncing the key pair across your devices through an encrypted cloud store (iCloud Keychain, Google Password Manager) rather than trusting one piece of hardware alone. The cryptographic model underneath — WebAuthn — is identical; what changed is that the private key can now travel with you.

This is no longer just an industry trend — it has formal regulatory backing

NIST's Digital Identity Guidelines (SP 800-63B, Revision 4) formally incorporated syncable authenticators — passkeys — into the federal standard, and industry commentary now describes FIDO2 as the emerging gold standard for phishing-resistant authentication. This is the answer to "is this becoming a new standard": yes, and it now has the weight of a federal digital-identity standard behind it, not just adoption by big tech companies.

Phishing-resistantStructurally, via origin binding — not procedurally, via user caution.
Nothing to steal in a breachThe server only ever stores public keys. A stolen database yields nothing an attacker can use to log in as anyone.
Fast for the userA fingerprint or face scan, no typing.
Needs modern browser/OS supportBroadly available now, but not on every legacy device a customer might use.
Account recovery is a real design problemIf someone loses every synced device, there must be a fallback — and that fallback is itself a security decision worth making deliberately, not an afterthought.
04

OAuth / OpenID Connect

The most commonly misunderstood item on this list — including what the "Oauth" in your question most likely refers to. Worth untangling carefully.

OAuth alone is not a login system

OAuth 2.0 is an authorization framework — it answers "can this app read my Google Calendar," not "who is this person." That's the same AuthN/AuthZ distinction from the companion auth reference, applied to a name that gets used loosely. Plain OAuth has no concept of "who logged in" at all — only "what was this token granted access to."

OpenID Connect (OIDC) is a thin identity layer built on top of OAuth specifically to answer the login question. It's what actually powers every "Sign in with Google" button. When people say "using OAuth to log in," they mean OIDC riding on OAuth's transport mechanism.

The payoff: OIDC's ID token is a JWT

This closes a loop from the companion reference. OIDC's core addition to plain OAuth is the ID token — and it is, structurally, exactly the JWT covered there: header, payload, signature, the same three Base64url-encoded segments. Google (or Apple, or whichever provider) signs it instead of your own server, and its payload carries standard identity claims — sub, email, name — instead of ones you defined yourself. Same anatomy, different issuer.

The flow: Authorization Code with PKCE

The historical "Implicit" flow — which returned tokens directly in the browser's URL — is now formally retired. Current OAuth security guidance (RFC 9700, folded into the OAuth 2.1 consolidation) requires the Authorization Code flow with PKCE for every client type, public or confidential, no exceptions. This is the one true modern flow to know:

  Browser              Manitou API                    Google
    │  "Sign in with Google" clicked          │                          │
    ├─────────────────────────────────────────▶│                          │
    │                       generate a random "code_verifier"             │
    │                       derive "code_challenge" from it                │
    │  redirect to Google, with code_challenge │                          │
    │◀──────────────────────────────────────────────────────────────────▶│
    │                                          │        user approves at Google
    │  redirect back with a one-time "code"    │                          │
    ├─────────────────────────────────────────▶│                          │
    │                       exchange code + original code_verifier         │
    │                       for tokens, server-to-server                   │
    │                                          ├─────────────────────────▶│
    │                                          │◀─────────────────────────┤
    │                                          │   { id_token, access_token }
    │  Manitou issues its OWN session/JWT       │                          │
    │◀─────────────────────────────────────────┤                          │

PKCE (Proof Key for Code Exchange) exists to stop an intercepted authorization code from being redeemed by anyone but the client that requested it — the code_verifier never travels in a URL, only its derived hash does, so a captured redirect alone isn't enough to steal the session.

What this actually looks like for Manitou

Adding "Sign in with Google" wouldn't replace your auth system — it would feed it. Google's ID token arrives, your backend verifies its signature came genuinely from Google, reads the verified email out of it, finds or creates the matching row in your existing users table, and issues your own normal JWT exactly as it does today. OIDC only ever replaces the credential-checking step; everything downstream — your role claim, your token issuing, your existing endpoints — stays identical.

No password to stealManitou never sees or stores a credential for these users at all.
Lower signup frictionOne click for anyone already signed into Google — a real, measurable conversion win for a storefront.
Third-party dependencyIf Google's identity service is down, or the user's Google account is compromised, that risk now touches your login too.
Real implementation complexityRedirect handling, state/CSRF protection, token verification against the provider's public keys — meaningfully more moving parts than issuing your own JWT.

SMS one-time codes

Familiar, cheap to explain to users — and the one method here with a formal regulatory downgrade attached to it as of the most recent NIST guidance.

  User                                    API                     SMS gateway
    │  login attempt                           │                          │
    ├─────────────────────────────────────────▶│                          │
    │                       generate a random 6-digit code, store briefly  │
    │                                          ├─────────────────────────▶│
    │                                          │                          ├──▶ 📱 "Your code: 482913"
    │  reads code from phone, types it in       │                          │
    ├─────────────────────────────────────────▶│                          │
    │                       compare, single use, short expiry              │
    │  access granted                          │                          │
This is no longer just "SMS isn't ideal" — it's now a formal classification

The newest revision of NIST's Digital Identity Guidelines (SP 800-63B-4) formally classifies SMS and phone-network one-time passcodes as a "restricted authenticator" — a new, explicit category. It isn't banned, but organizations using it now carry documented obligations: a risk assessment, a migration plan away from it, and user notification of the risk. This is a meaningfully stronger stance than the previous revision's general caution.

Why regulators moved on this specifically

SIM swappingAn attacker convinces (or bribes, or social-engineers) a carrier to port your number to their SIM. Every SMS meant for you now arrives on their phone.
SS7 interceptionThe decades-old telecom signaling protocol carrying SMS has known, demonstrated interception weaknesses — attackers with the right access can read texts in transit without touching your phone at all.
Number porting fraudSimilar to SIM swapping, exploiting the number-transfer process between carriers directly.
No phishing resistanceA fake login page can simply ask for the code the same moment it asks for the password, relaying it to the real site in real time — an adversary-in-the-middle attack that defeats SMS OTP just as easily as a password.

If it's used anyway — the concrete mitigations NIST specifies

SMS OTP isn't prohibited outright, and the standard is specific about what's required to use it responsibly: rate-limit and throttle failed attempts (capping online guessing at no more than 100 consecutive failures), enforce that each code works exactly once, and never deliver a code over email or VoIP — only genuine mobile carrier SMS. None of these mitigations address the interception-based attacks above; they only slow down brute forcing.

Zero learning curveEvery phone user already understands "type the code you were texted."
No app install requiredWorks on any phone capable of receiving a text — a real accessibility advantage over an authenticator app or a passkey-capable device.
Formally restricted by NISTPermitted only with a documented risk assessment and migration roadmap.
Vulnerable to interceptionSIM swap, SS7, and adversary-in-the-middle relay all defeat it, none of which the code-formatting mitigations above address.
Ongoing per-message costUnlike every other method here, each attempt has a direct, recurring dollar cost via an SMS gateway.
International delivery is unreliableCarrier delays and filtering vary widely outside the country a service is built for.
06

Identity proofing (ID.me)

A different question entirely from everything above — and the reason it belongs in its own section rather than as a fifth entry in the comparison table.

Authentication vs. identity proofing

Every method in §02–§05 answers: "are you the same person who created this account?" They compare you against a credential you registered earlier. None of them care who you are in the real world — an account registered as batman@example.com authenticates exactly as well as one registered with your legal name.

Identity proofing answers a different question: "are you a specific, verifiable, real-world legal person?" That's ID.me's actual product. It happens before or alongside authentication, not instead of it.

What ID.me actually does

Verification methods include scanning a government-issued document with machine vision, liveness detection matching a selfie against the photo on that document, confirming the SIM in your phone is associated with the identity you're claiming, and — where automated checks fail — a live video call with a trained "Trusted Referee." It's accredited against NIST's IAL2/AAL2 identity-assurance standard.

Note that IAL (Identity Assurance Level) is a separate scale from the AAL in §08. AAL measures how confidently you proved you hold a credential; IAL measures how confidently that credential was tied to a real human in the first place. Different questions, different scales — a system can be strong on one and absent on the other.

Where it's genuinely used

Adoption spans 21 federal agencies, 50 state agencies, and more than 70 healthcare organizations. Concrete deployments include Medicare.gov beneficiary verification, FINRA's regulatory platform for financial-industry account administrators handling sensitive data, and the IRS — where it's the only online path to taxpayer tools. The common thread is unmistakable: tax records, government benefits, regulated financial access. High-stakes, fraud-critical contexts where the friction of uploading a driver's license is genuinely worth it.

The e-commerce exception worth knowing

More than 600 consumer brands use ID.me — but for a narrow purpose: verifying eligibility for a segment, not general login. This is the military, student, teacher, and first-responder discount use case. The user proves they're active-duty military once, and the store applies a discount. It sits alongside normal authentication rather than replacing it.

Real fraud preventionStops account creation by someone impersonating a real person — something no amount of password strength addresses.
Regulatory acceptanceFederally accredited, which is why agencies can rely on it for benefits access.
Heavy user frictionUploading a government ID and taking a verification selfie is a very different ask than typing a password. For a T-shirt purchase it's wildly disproportionate.
Per-verification costTiered pricing based on volume of verifications requested — a real recurring expense.
Privacy considerationsBiometric and government-document handling has drawn public scrutiny, and adds compliance surface most stores don't want.
Verdict for Manitou

Not applicable as an authentication method — it isn't one. The only realistic future hooks are narrow: a military/student discount program in a cloned store, or age verification if a grocery clone ever sold alcohol. Both are optional features layered on top of your existing auth, never replacements for it.

07

IAM and CIAM

Also not an authentication method — a category of platform that packages several of the methods above, plus user management, into a managed service you rent instead of build.

IAM vs. CIAM — the distinction that matters

TermManagesTypical concerns
IAM Internal workforce identity — employees accessing enterprise systems. Provisioning and deprovisioning staff, role hierarchies, least-privilege access, audit trails.
CIAM External customer identity across websites, mobile apps, and services. Signup conversion, social login, consent and privacy, scaling to millions of accounts.

CIAM focuses on managing external customer identities across websites, mobile apps, and digital services, while IAM is typically used for internal workforce identity management, controlling employee access to enterprise applications. For Manitou, the relevant category is CIAM — you're managing shoppers, not staff. There's exactly one internal user, and seed.py already created them.

You already have AWS IAM in the plan — and it's a third thing

PROJECT_PLAN.md Section 7 lists AWS IAM for managing which AWS services and people can touch your infrastructure. That's cloud resource permissioning — who can read the S3 bucket, which role the container assumes. It has nothing to do with your customers logging in. AWS Cognito is the separate AWS service that would handle customer identity, and it's noted in the plan as an optional alternative to rolling your own JWT auth.

What a CIAM platform actually gives you

These platforms cover the core of customer identity — authentication, authorization, consent, and user management — as managed infrastructure. In practice you'd stop writing the code you're currently building in Phase 2, and instead configure: password login, social login (OIDC), passkeys, MFA, password reset flows, email verification, session management, and an admin console for user support.

The notable names, for orientation: Auth0 (now part of Okta) for breadth and enterprise federation, Amazon Cognito for teams already on AWS, Clerk for React and Next.js developer experience, plus Descope, Stytch, WorkOS, FusionAuth, and Keycloak. Amazon Cognito is AWS's managed service for authentication and user management, handling infrastructure, scaling, and availability automatically — a common choice for teams already on AWS, with the unique advantage of direct AWS IAM integration.

The honest tradeoff

Enormous time savingsPasskeys, social login, MFA, and reset flows all work on day one rather than being months of work each.
Security expertise includedToken handling, rotation, and breach-detection built by people who do only this.
Compliance groundworkSOC 2, ISO 27001, HIPAA certifications the vendor already holds.
Cost scales with usersPricing is typically per monthly active user (MAU), and cost curves diverge sharply as you grow.
Vendor lock-inAuth flow changes often require code even for simple updates, and migrating away later is real work. Teams frequently outgrow their first choice as products scale.
You learn lessThe whole point is that someone else solved it. For a learning project, that's a cost, not a benefit.
Verdict for Manitou — and the pattern you'll recognize

This is the same fork as Django's admin panel, WooCommerce, and MedusaJS: a mature platform that does the work for you, versus building it yourself to understand it. Same answer as those: for a business optimizing to ship fast, a CIAM platform is often the right call. For your stated goal — mastering full-stack development from first principles — building the auth yourself is the point.

Worth knowing the category exists, and worth knowing Cognito sits closest to your stack if you ever change your mind mid-project. But nothing here argues for changing course now.

08

Assurance levels

NIST's Authenticator Assurance Levels (AAL) give a shared vocabulary for "how confident is this, really" — useful for placing all four methods on one scale rather than debating them in isolation.

LevelRequiresReachable by
AAL1Any single factorPassword alone
AAL2Two distinct factorsPassword + SMS OTP; password + authenticator app
AAL3A hardware-based, verifier-impersonation-resistant factorWebAuthn/FIDO2 only, among the methods here
The line that matters most

OTP-based methods — including SMS — can support AAL1 up to AAL2, but can never reach AAL3, because they aren't verifier-impersonation-resistant: a convincing fake verifier can still successfully collect and relay the code. WebAuthn is the only method in this document built to resist that specific attack, by design, at the protocol level — which is the technical grounding behind calling it "phishing-resistant" rather than just "safer."

What fits Manitou

Password + bcrypt + JWTKeep — already the plan

Remains the correct baseline. It's the only method here with no external dependency, and Section 3 already settled it. Nothing above is an argument to change course.

WebAuthn / FIDO2 (passkeys)Strong future addition

The best candidate for a genuine security upgrade later — offer it alongside passwords, not instead of them, since not every customer's device supports it yet. A real Phase 8 hardening item, and one with growing regulatory backing behind it.

OAuth / OIDC ("Sign in with Google")Reasonable future addition

A conversion-rate feature more than a security one — it lowers signup friction for customers already signed into Google or Apple. Feeds into your existing JWT issuing rather than replacing it; a natural post-launch enhancement once the core store works end to end.

SMS one-time codesNot recommended

Given the 2026 NIST "restricted" classification and the concrete SIM-swap/SS7 exposure, this isn't worth adding as a primary or secondary factor for Manitou. If a second factor is ever genuinely needed, an authenticator app (TOTP) or WebAuthn itself both reach AAL2+ without the interception risk, at no per-message cost.

Identity proofing (ID.me)Not applicable

Not an authentication method, so it isn't an alternative to anything above. Government-ID verification for a T-shirt purchase is disproportionate friction for the actual risk. The only realistic hooks are narrow optional features — a military/student discount program, or age verification if a grocery clone sold alcohol — layered on top of your existing auth.

CIAM platform (Auth0, Cognito, Clerk)Against the project's purpose

Would genuinely save months and give you passkeys, social login, and MFA on day one. It would also mean not building the thing you set out to learn. Same fork as Django's admin, WooCommerce, and MedusaJS — and the same answer. If you ever do change your mind, Cognito sits closest to your existing AWS stack.

The honest bottom line

Nothing here changes what to build right now. It's context for later — when Phase 8 hardening comes around, WebAuthn is the upgrade worth prioritizing, OIDC is worth adding if signup friction turns out to matter, and SMS is the one option this document actively steers away from.

Glossary

FIDO2The umbrella standard combining WebAuthn (the browser-facing API) and CTAP (the protocol for talking to external authenticators like a YubiKey).
WebAuthnThe W3C API standard letting a browser create and use public-key credentials for login.
PasskeyA WebAuthn credential that syncs across a user's devices via an encrypted cloud store, rather than being bound to one piece of hardware.
Relying partyThe service asking for authentication — Manitou's API, in this document's diagrams.
AuthenticatorThe thing holding the private key: a phone, a laptop's secure enclave, or a hardware security key.
Platform authenticatorAn authenticator built into the device — Face ID, Windows Hello.
Roaming authenticatorA separate, portable authenticator — a physical security key.
OAuth 2.0A framework for delegated authorization — letting one application access resources on another service on a user's behalf.
OIDC (OpenID Connect)An identity layer built on top of OAuth 2.0, adding the ID token and standard identity claims — what actually powers social login.

OTPOne-Time Password/code — a short-lived credential valid for a single use.
SIM swapAn attack porting a victim's phone number to an attacker-controlled SIM, redirecting their SMS messages.
SS7The decades-old telecom signaling protocol carrying SMS, with known interception weaknesses.
Restricted authenticatorA new NIST classification (SP 800-63B-4) for authenticator types — currently SMS/phone OTP — permitted only with documented risk mitigation.

AALAuthenticator Assurance Level — NIST's three-tier scale (AAL1–AAL3) for how confidently an authentication method establishes identity.
IALIdentity Assurance Level — a separate NIST scale for how confidently a credential was tied to a real-world person in the first place. AAL and IAL answer different questions.
Identity proofingVerifying someone is a specific real-world legal person, typically via government documents and biometrics. What ID.me does; distinct from authentication.
IAMIdentity and Access Management — managing internal workforce identity and what employees can access. Also the name of AWS's service for permissioning cloud resources.
CIAMCustomer Identity and Access Management — the same discipline aimed at external customers rather than staff. The relevant category for a storefront.
MAUMonthly Active Users — the usual billing unit for CIAM platforms, and the reason their costs scale with your growth.
Trusted RefereeA trained human reviewer who verifies identity over video call when automated document checks fail.
