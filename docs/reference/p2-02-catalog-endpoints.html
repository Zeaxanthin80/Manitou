00

What's an endpoint

You already know this from the other side. Every time a browser loads a page, it sends an HTTP request to a URL and gets a response back. An endpoint is just one URL your server knows how to answer.

The difference here is what comes back. A web server returns HTML for a browser to render. An API endpoint returns JSON — structured data for a program to use. Same protocol, same URLs, same status codes; only the body differs.

  BROWSER LOADING A PAGE              API ENDPOINT

  GET /products.html                 GET /products
  → <html><body>...</body></html>     → {"items": [...], "total": 3}
     for a human to look at              for a program to use

In Phase 3, your Next.js storefront will call these endpoints and turn the JSON into HTML. That's the whole shape of the system: the API produces data, the web app produces pages. Phase 7's mobile apps call the same endpoints and produce native screens instead.

The four you built in task 2

EndpointAnswers the question
GET /categoriesWhat categories does this store have?
GET /categories/{slug}Tell me about this one category.
GET /productsShow me products — optionally filtered and paged.
GET /products/{slug}Tell me everything about this one product.

The pattern — a collection and an item within it — is the core of REST. It repeats for carts, orders, and everything else you'll add.

GET means read

Task 2 is entirely GET: fetch data, change nothing. Repeating a GET a thousand times has the same effect as doing it once. That property is called idempotence, and it's why browsers and caches can safely retry a GET but will warn you before re-submitting a POST.

Task 3 introduces POST, PATCH, and DELETE — the verbs that change things, which is where authentication starts to matter.

01

URL anatomy

Two different ways to pass information in, and knowing which is which explains most of the function signatures in catalog.py.

/products?category=apparel&limit=20&offset=0

Path

Which resource you want. Identifies the thing.

/products
/products/canvas-tote-bag
/categories/t-shirts

Query — filters

Narrows the result. Optional; the endpoint works without them.

?category=apparel
?q=tee

Query — paging

How much of the result you want back at once.

?limit=20
&offset=40

FastAPI maps both onto ordinary Python function arguments. A name that appears in the route path becomes a path parameter; anything else becomes a query parameter:

@router.get("/products/{slug}")
def get_product(slug: str, ...):        # "slug" is in the path → path param


@router.get("/products")
def list_products(
    category: str | None = Query(None),  # not in the path → query param
    limit: int = Query(20, ge=1, le=100),
):

The type annotations aren't decoration. limit: int means FastAPI converts and validates before your code runs — ?limit=abc is rejected automatically, and ge=1, le=100 enforces the range. You never write that check yourself.

Rule of thumb

Path identifies what. Query modifies how. A product's identity belongs in the path; a filter over many products belongs in the query. That's why it's /products/canvas-tote-bag and not /products?slug=canvas-tote-bag.

02

The slug

A short, lowercase, hyphenated, URL-safe version of a name. The word comes from newspaper typesetting — a "slug" was the short label editors used to refer to a story in progress.

  Product name   Classic Cotton Tee
  Slug           classic-cotton-tee

  /products/classic-cotton-tee     readable, shareable, memorable
  /products/12                     works, tells a human nothing

Why the database has a slug column at all

URL-safeNo spaces, accents, apostrophes, or & — nothing needing percent-encoding. Café & Cream becomes cafe-cream.
ReadableA person can look at the URL and know what's on the page. That matters when links get shared.
SEOSearch engines weight words in the URL. Section 3 of PROJECT_PLAN.md cites SEO as a reason for choosing Next.js — slugs are the same argument at the data layer.
StableThe slug is stored, not computed from the name. Rename the product for display and old links keep working.
Why the id still exists

Both are unique, so both could identify a product. The split Manitou uses: slug for public reads, id for admin writes.

The reasoning is that ids never change, while a slug is human-facing text someone might want to edit. An admin endpoint saying PATCH /admin/products/12 keeps working through any rename; the same endpoint keyed on a slug would break the moment the slug it references is the thing being changed.

The products.slug and categories.slug columns carry unique constraints, so the database itself guarantees a slug resolves to exactly one row — a lookup by slug is as safe as a lookup by primary key. Section 6.6 also indexes them, which is what keeps that lookup fast.

03

Status codes

HTTP status codes, not HTML. HTML is the document language a browser renders; HTTP is the protocol that carries any response — JSON, an image, a PDF. Every response has a status code regardless of what's in the body.

The first digit tells you the category, and that alone gets you most of the way:

RangeMeaningWhose fault
2xxSuccess—
3xxRedirect — look elsewhere—
4xxThe request was wrongThe client's
5xxThe server brokeYours
The distinction that matters most

4xx means the caller made a mistake. 5xx means your code did. A 500 in your logs is always a bug — something raised an exception you didn't handle. A 404 is not a bug; it's the API correctly reporting that what was asked for doesn't exist.

This is why task 1 caught the duplicate-email IntegrityError and returned 409. Letting the database error escape would produce a 500 — telling the caller "the server is broken" when in truth their request was simply invalid.

The ones task 2 uses

CodeNameWhen Manitou returns it
200OKThe product or list was found and is in the body.
404Not FoundNo product with that slug — or it exists but is is_active = false (see §10).
422Unprocessable EntityThe request was malformed: ?limit=999 exceeds the cap, or ?limit=abc isn't a number. FastAPI returns this automatically from the type annotations.

Task 1 added 201 Created (register), 401 Unauthorized (no or bad token), 403 Forbidden (valid token, wrong role), and 409 Conflict (duplicate email). Those seven cover nearly everything the API will ever need.

Why 422 rather than 400

Both mean "bad request." 400 classically means the request was malformed at the HTTP level — broken syntax. 422 means the syntax was fine but the content failed validation: well-formed JSON with a value out of range. FastAPI uses 422 for all Pydantic validation failures, which is why you see it rather than 400.

04

Request lifecycle

What actually happens between curl and the JSON coming back. Five stages, and every endpoint you write from here follows the same path.

GET /products?category=apparel&limit=20

  1. ROUTING            FastAPI matches the URL to list_products()
       │
       ▼
  2. VALIDATION         Query params parsed and type-checked
       │                  limit: int, ge=1, le=100
       │                  fails ──▶ 422, your code never runs
       ▼
  3. DEPENDENCIES       Depends(get_db) opens a database session
       │                  (task 1 also ran get_current_user here)
       ▼
  4. YOUR CODE          build the query, run it, get ORM objects back
       │                  Product, ProductImage, Category ...
       ▼
  5. SERIALISATION      response_model converts ORM objects → JSON
       │                  anything not in the schema is dropped
       ▼
  200 OK  {"items": [...], "total": 3}

Stages 1, 2, 3, and 5 are FastAPI's work. You only write stage 4 — which is why the endpoint functions are short. The framework handles parsing, validating, injecting, and serialising.

Why stage 5 is a security feature

response_model doesn't just format the output — it filters it. A field absent from the schema cannot appear in the response, even if the ORM object has it.

That's the mechanism behind UserRead in task 1 having no password_hash. The User object loaded from the database has one; the schema drops it. Protection by construction rather than by remembering.

The dependency in stage 3

db: Session = Depends(get_db) means "before running this function, call get_db() and pass me the result." FastAPI also runs the cleanup half afterwards, which is why get_db in db.py is written with try/finally — the session is closed even if the endpoint raises. Forgetting that is how a connection pool leaks until the API stops responding.

05

List vs detail

The same product returns two different shapes depending on which endpoint you ask. That's deliberate, and it's about how much work the database does.

ProductListItemCatalogue grid
{
  "id": 7, "name": "Classic Cotton Tee",
  "slug": "classic-cotton-tee",
  "base_price": "24.00", "unit_of_measure": "each",
  "category_id": 2,
  "primary_image": { "url": "...", "alt_text": "...", "is_primary": true }
}

Exactly what a grid tile needs: a name, a price, one image, and a link. No variants. No description.

ProductDetailProduct page
{
  "id": 7, "name": "Classic Cotton Tee", "description": "...",
  "base_price": "24.00", "category": { ... },
  "images": [ ... ],
  "variants": [
    { "sku": "TEE-CLS-S-BLK", "attributes": {"size":"S","color":"Black"},
      "price": "24.00", "in_stock": true },
    ...
  ]
}

Everything, because the product page renders a size picker, a colour picker, and per-variant availability.

Why not just return everything, always

A catalogue page showing 50 products would load 50 descriptions, every image, and every variant with its stock row — to render tiles that display a name and a price. That's hundreds of rows fetched, serialised, and sent over the network so the client can throw them away.

With three seeded products this costs nothing and the difference is invisible. At three thousand it's the difference between a fast page and a slow one. The same reasoning drives the next two sections.

Two details worth noticing

price The variant's price is the effective price — price_override when set, otherwise the product's base_price. The API resolves that rule so no client has to know it. TEE-GRA-L-NVY returns 32.00 against a 29.00 base.
in_stock A boolean, not quantity_available. Publishing exact counts lets a competitor infer your sales volume by polling; a storefront only needs to know whether it can be bought. The vendor portal gets real numbers from the admin endpoints in task 6.
06

The N+1 problem

The single most common performance bug in ORM code. It is invisible in development and severe in production, which is exactly what makes it worth understanding now.

Where it comes from

SQLAlchemy relationships are lazy by default. product.images isn't loaded when the product is — it's fetched the first time you touch it. That's usually helpful: you don't pay for data you never read.

But put it in a loop and each iteration silently fires its own query:

products = db.scalars(select(Product)).all()   # 1 query

for p in products:
    print(p.images)                           # 1 query — every time round

One query for the list, then N more — one per product. Hence N+1.

  LAZY — 50 products

  SELECT * FROM products LIMIT 50;                    ← 1
  SELECT * FROM product_images WHERE product_id = 1;  ← 2
  SELECT * FROM product_images WHERE product_id = 2;  ← 3
  SELECT * FROM product_images WHERE product_id = 3;  ← 4
  ... 47 more ...
  SELECT * FROM product_images WHERE product_id = 50; ← 51
Why it hides

Each individual query is fast — a millisecond, on an indexed column. Nothing errors. Nothing looks wrong. With three seeded products you'd never notice four queries instead of two.

What kills you is the round trip. Every query is a separate network hop to the database, and in production that database is on another machine. Fifty round trips at 2ms each is 100ms of pure waiting. Scale to 1,000 concurrent users — Manitou's stated target — and you've multiplied your database's query load by fifty for no benefit whatsoever.

The fix, measured

Adding .options(selectinload(Product.images)) tells SQLAlchemy to fetch all the images in one extra query instead of one per product. Measured on the real endpoint:

1 product3 queries
2 products3 queries
3 products3 queries
50, lazy51 queries

The count stays flat as the page grows. That's the property you want, and it's the actual test — not "does the endpoint work," but "does the query count change when the result size changes."

  1. SELECT count(*) FROM products WHERE is_active     the total
  2. SELECT * FROM products WHERE is_active LIMIT 20   the page
  3. SELECT * FROM product_images WHERE product_id IN (...)  all images at once
07

Eager loading

Two strategies for loading related rows up front, and they behave differently enough that picking the wrong one causes its own bug.

selectinloadUsed in Manitou
SELECT * FROM products WHERE is_active LIMIT 20;
SELECT * FROM product_images WHERE product_id IN (1,2,3,...,20);

A second query using IN. Two queries total, however many products. Each row comes back once, so LIMIT means exactly what you expect.

joinedloadRight for one-to-one
SELECT * FROM products
  LEFT JOIN product_images ON ...
  WHERE is_active LIMIT 20;

One query with a JOIN. Fine for a one-to-one relationship — a variant and its inventory row.

Dangerous for one-to-many: a product with 4 images produces 4 rows, so LIMIT 20 stops after 20 rows, not 20 products. You silently get five products back.

A rule you can apply without thinking

Collections (a product's images, a cart's items) → selectinload. Single related objects (a product's category) → joinedload is fine, and one fewer round trip.

When paginating, always selectinload collections. Mixing LIMIT with a one-to-many JOIN is a classic source of "why did my page return five items."

Where the detail endpoint uses it

select(Product).where(...).options(
    selectinload(Product.images),     # collection
    selectinload(Product.variants),   # collection
    selectinload(Product.category),   # single
)

Without these, building the response would touch product.images, product.variants, and then variant.inventory for every variant — a nested N+1, which is the same bug one level deeper.

08

Recursive CTE

CTE stands for Common Table Expression — a named temporary result set that exists for the duration of one query. A recursive CTE can refer to itself, which is how SQL walks a tree.

A plain CTE first

Without recursion, a CTE is just a way to name a subquery so the rest of the statement reads better:

WITH cheap_products AS (
    SELECT * FROM products WHERE base_price < 25
)
SELECT * FROM cheap_products WHERE is_active;

Nothing clever — the same result as a subquery, written top-to-bottom instead of inside-out.

The problem recursion solves

Categories form a tree, because categories.parent_id points at another row in categories. The seeded store looks like this:

  apparel                    0 products directly
    ├── t-shirts             2 products
    └── accessories          1 product
The bug this avoids

A shopper clicks Apparel. The obvious query — WHERE category_id = (id of apparel) — returns zero products, because every product hangs off a child category. The top-level category a shopper is most likely to click shows an empty store.

You could sidestep it by filing every product under a leaf category and never linking to parents. But that constrains the store's navigation to work around a query limitation, which is the wrong way round.

How the recursion works

WITH RECURSIVE subtree AS (

    SELECT id FROM categories WHERE slug = 'apparel'     ← anchor: the start

    UNION ALL

    SELECT c.id FROM categories c                          ← recursive: find children
      JOIN subtree s ON c.parent_id = s.id                   of what we have so far
)
SELECT * FROM products WHERE category_id IN (SELECT id FROM subtree);

Two halves joined by UNION ALL. The first runs once. The second runs repeatedly, each pass finding children of whatever the previous pass found — and stops on its own when a pass returns nothing.

PASS 1  anchor          → {apparel}
PASS 2  children of {apparel}      → {t-shirts, accessories}
PASS 3  children of those          → {} — nothing new, stop

RESULT  {apparel, t-shirts, accessories}  →  3 products
Why this and not a Python loop

You could load all categories, walk the tree in Python, collect the ids, then query. It works, and it's easier to read if you've never seen a CTE.

But it's several round trips instead of one, it moves work the database is specifically built for into the application, and it gets slower as the tree grows. The CTE handles any depth — add a fourth level tomorrow and not a line changes.

The same thing in SQLAlchemy

anchor = select(Category.id).where(Category.slug == slug)
subtree = anchor.cte(name="subtree", recursive=True)
subtree = subtree.union_all(
    select(Category.id).join(subtree, Category.parent_id == subtree.c.id)
)

Line for line the same structure as the SQL: anchor, mark it recursive, union the child lookup onto it. subtree.c.id is how you reference a column of the CTE — .c for "columns."

09

Filter, search, page

Three query parameters, three separate concerns, all combinable on the same endpoint.

Search — and an honest limitation

Product.name.ilike(f"%{q}%")     →   WHERE name ILIKE '%tee%'

ILIKE is PostgreSQL's case-insensitive LIKE. % matches any sequence of characters, so %tee% finds "tee" anywhere in the name — which is why ?q=tee and ?q=TEE both return both t-shirts.

The leading wildcard cannot use an index

An index works like a dictionary: sorted, so you can jump to the right place. 'tee%' can use one — everything starting with "tee" is contiguous. '%tee%' cannot, because a match could be anywhere in any word. The database must read every row.

Fine at this catalogue size, genuinely slow at 100,000 products. The real fix is PostgreSQL full-text search (tsvector with a GIN index), which Section 12 of PROJECT_PLAN.md explicitly defers until after v1. This is a known, named limitation rather than an oversight.

Pagination

?limit=20&offset=0     first 20
?limit=20&offset=20    next 20

The response carries total alongside the items, so a client can render "page 2 of 7" without fetching everything just to count it. That total is the first of the three queries from §06.

Always cap the limit

le=100 means ?limit=999 returns 422. Without a cap, anyone can request the entire catalogue in one call — and with a large table that's a slow query holding a connection open. Repeat it a few times concurrently and you've taken the API down without needing an attack, just a careless client.

Combining them

GET /products?category=apparel&q=tee&limit=10

  1. resolve "apparel" to its subtree via the recursive CTE
  2. WHERE is_active AND category_id IN (subtree) AND name ILIKE '%tee%'
  3. count the total, then fetch one page of 10

The conditions accumulate in a list and are applied together, so any combination works without a special case per pairing.

10

Visibility

Every public query filters is_active. The interesting part is what happens on the detail endpoint, which is where this is usually got wrong.

Section 6.3 describes is_active as a way to "hide products without deleting them" — a product that's out of season, or not launched yet. Deleting it would break order history, since past order_items reference it.

Filtering the list is not enough

If only GET /products checks is_active, a deactivated product vanishes from the catalogue but GET /products/classic-cotton-tee still returns 200 with the full product. Anyone with the link — a bookmark, a shared URL, a search result — still sees it.

That isn't hidden. It's unlisted, which is a different and much weaker guarantee.

So the detail query carries the same condition, and an inactive product returns 404:

select(Product).where(
    Product.slug == slug,
    Product.is_active.is_(True),
)
if product is None:
    raise HTTPException(404, "Product not found")
404, not 403

403 would mean "this exists and you may not see it" — which confirms the product exists. 404 says nothing at all. For a hidden product that's the right answer: a competitor shouldn't be able to probe slugs to discover what you're about to launch.

Same reasoning as task 1's login endpoint returning one identical error for both an unknown email and a wrong password. Don't leak existence.

Public, deliberately

These four endpoints have no Depends(get_current_user) — no token required. A storefront catalogue must be readable by anyone, including search engine crawlers, before any account exists.

That's why the split matters in FastAPI: a route with no auth dependency is visibly public at a glance. Task 6's admin endpoints will carry Depends(require_admin), and those do see inactive products — the vendor needs to find a product in order to reactivate it.

11

Anti-patterns

Mistakes specific to read endpoints, roughly in order of how much damage they cause.

Unbounded list endpoints

No limit, or a limit with no maximum. One request can then pull the whole table — a slow query holding a database connection, trivially repeatable. This is how an API falls over without anyone attacking it.

N+1 queries

Touching a lazy relationship inside a loop. Invisible with seed data, crippling with real data. If a response contains a list of things that each contain a list of things, check the query count.

Filtering visibility on the list but not the detail

A hidden product still reachable by direct URL. Every query that can return a row must apply the same visibility rule.

Returning ORM objects without a response model

Whatever the model has ends up in the JSON — including columns added later that were never meant to be public. The schema is the contract; without one, the database table becomes the contract by accident.

String-formatting values into SQL

f"WHERE name = '{q}'" is SQL injection. Passing q as a parameter — which is what ilike(f"%{q}%") does, since the f-string builds the pattern, not the SQL — keeps the value separate from the statement.

Leaking exact stock counts

Publishing quantity_available lets anyone infer your sales volume by polling. Return a boolean publicly; keep real numbers for the vendor portal.

Returning 200 with an empty body for "not found"

Forces every client to check the body to discover failure. The status code exists precisely so they don't have to.

Response modelThe Pydantic schema shaping and filtering the response body.
SerialisationConverting Python objects into JSON for transmission.
ORMObject-Relational Mapper — SQLAlchemy, mapping database rows to Python objects.

Eager loadingFetching related rows up front, deliberately.

joinedloadEager loading via a JOIN. Correct for single related objects; breaks LIMIT on collections.
